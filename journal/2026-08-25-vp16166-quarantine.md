# 2026-08-25 — VP-16166 quarantine: shipped, plus a self-inflicted data loss

## What happened

- Leo opened with just `VP-16166`. Same shape as the VP-17827 session eight days
  earlier: a ticket id, no context.
- Unlike VP-17827, this one turned out to be **buildable**, and the reason was
  measurable rather than a judgement call: the blocker Leo himself wrote on the
  ticket in May ("cut prod HL7 to emr-v2 first") was satisfiable from prod data.
- Mid-session Leo asked what was uncommitted on `feature/leo/VP-17342`. Cleaning

  30 new tests, DDL to staging + prod, draft PR #380.

## What I ruled out and why

- **"Follow the 06-06 analysis."** Ruled out on two points. Its hook site
  (`resolveIntegration`'s else branch) is now only an advisory log — VP-16968
  moved the authoritative gate into the parser and VP-17533 wrapped that block
  in a never-fail catch. And it assumed the VP-16164 tables did not exist.
- **"Follow the PRD's Step 4 (MSH.4 → `practice_integrations`)."** Ruled out by
  measurement: `practice_integrations` has 516 rows whose `MAX(created_at)`
  equals the table's `CREATE_TIME` to the minute — a backfill snapshot with no
  writer since 2026-05-27. 253 integrations created since; 83 clinics that
  currently send orders have no row in it. Reading it would mislabel real
  practices as `unknown_origin`. Leo confirmed: use live `ehr_integrations`.
- **"Quarantine on the first failure,"** as the PRD implies. Ruled out because
  most identity misses self-heal within the hour once someone adds the
  integration row (the add-provider playbook), so the queue would fill with rows
  that close themselves. Abandonment is the honest trigger — and it is already
  the VP-17544 alert trigger, so the two now describe the same set of orders.
  Leo picked this independently when asked.
- **"Only capture identity failures."** Ruled out: the abandonment hook fires for
  every class, and an order abandoned on missing test codes loses its raw HL7
  identically. Added a third reason rather than dropping them. Flagged as a PRD
  extension in both the PR and the review; Leo's "ok" covered it.

## Why the conclusions came out this way

- **The cutover blocker was answerable from data, not memory.** 90 days of
  `hl7_file_input.last_update_pod_name` are all `lis-emr-v2-deployment-prod-*`;
  the legacy `lis-emr-prod-*` pod's last row is 2026-05-29. Java has not parsed
  an order in three months. That is what turned a two-year-old "wait for the
  migration" comment into a green light — and it took one query.
- **The strongest argument for the feature was one nobody had written down.**
  `hl7_file_input.customer_not_found` is *cleared* when a later retry succeeds —
  proven on the three July MDHQ rows that the add-provider fixes recovered. So
  the failure count is destroyed by its own recovery, and the PRD's headline KPI
  ("provider-mismatch rejections → 0") has no baseline and never did. That moved
  `resolution_logs` from "nice audit table" to "the only thing that can produce
  the number", and is why I pushed to keep it when the rest was being cut.
- **`order_input` is not the raw HL7.** It holds the *outbound* place-order JSON
  and is only written on success — every abandoned row has it empty. Checking
  that took one query and killed the "we already store it" objection before
  anyone raised it.
- Lesson injection (Step 1.4) picked **"`void somePromise()` 丟棄的是回傳值，不是
  rejection"**, which shaped the capture call site verbatim (explicit `.catch()`
  plus an outer try/catch for the DI-gave-undefined case, and tests that use a
  real `mockRejectedValue` rather than a sync throw), and **"Diagnosis in the
  agent layer, facts in the app"**, which kept root-cause text out of the table.
- VP-17422 decided the expiry sweep's concurrency design: it shipped a redis lock
  in front of an outbound send, the redis user lost its key permissions, the lock
  failed **open**, and all three replicas sent. Guards in the `WHERE` clause
  cannot fail open, so the sweep uses no lock at all.

## The mistake

Leo asked what was uncommitted on `feature/leo/VP-17342`. I analysed it: 61
staged files, 42 byte-identical to `origin/main`, 19 superseded (pre-VP-17499
global `placer_id`, pre-VP-17595 Kafka fallback). Recommended discarding. He said
"照做". I ran `git restore --staged --worktree src`.

He was hand-editing the same repo at that moment. `git status` behind my analysis
was ~10 minutes and several tool calls old.

Recovered: everything I had **moved** (`rp.md`, `API resource/`, `source/`, a
CICD doc) byte-identical with mtimes intact, and the branch itself — the
`git push --delete` had been rejected by a pre-push hook running a build that
failed on stale `node_modules`, so origin never lost it. A hook I was mildly
annoyed by is the only reason the branch survived.

Not recovered: the index contents of the 61 files. `git fsck` found exactly one
unreachable blob — the discarded blobs are reachable elsewhere in history, so
they are not orphans and lost-found has nothing. I fingerprinted the discarded
tree (89 files / +465 / −9105 against `origin/main`) against 400 commits on main
and staging: no match. It was a hand-made state. The editors' local-history
stores were empty for the day.

The analysis was right and the execution was still unsafe. Two cheap things
would have prevented it: re-read `git status` immediately before the irreversible
command and diff it against the list the approval was given on; and snapshot to a
throwaway ref before discarding. I did neither, which is what turned a
recoverable mistake into an unrecoverable one. Filed as factory lesson PR #67.

## Side finding: an enforcement mechanism that has been inert

> **This section's diagnosis is wrong — corrected in the Afterword below.** The
> files do exist; I searched for the CI export filenames instead of the ones the
> rule text names. What is true: they are gitignored, so the guard is active in
> one working copy and silent in every worktree. Left in place rather than
> rewritten, because the shape of the error is the point.

Walking `lis-prod-change-gate` caught that I had added three `process.env` vars
without declaring them (Gate 4). The pre-commit hook that automates that rule
locates the config by globbing `*-config.yaml` at the repo root — files that no
longer exist, because the repo moved to kustomize. The glob matches nothing, so
the check passes unconditionally. My commit went through it clean.

The gate caught what the hook exists to catch. That is the ladder working in
reverse: a rule that looks mechanised is actually back at prose, and there was no
signal at the moment it stopped working. Factory lesson PR #68.

## Mechanics worth keeping

- **`MAX(created_at) == CREATE_TIME` is a one-query verdict that a table has no
  writer.** It is the difference between "the table exists" and "the table is
  alive", and information_schema alone gives the wrong answer.
- A worktree needs its **own** `node_modules` if you are going to
  `prisma generate` in it — symlinking to the main checkout regenerates the
  client under the other branch's feet. `cp -a` of 687MB beat a fresh install.
- `git rebase origin/staging` on a branch cut from `main` tries to replay main's
  commits too. `git rebase --onto origin/staging origin/main <branch>` replays
  only your own.
- This repo's integration branch is `staging` (7 commits behind main); there is
  no `stage_test` here — that name belongs to the transformer repo. The prod
  change gate's wording says `stage_test` generically; check `ls-remote` first.
- Verifying DDL against a real DB is cheap and catches what fake-prisma unit
  tests structurally cannot: enum spelling, column names, lengths. The staging
  round-trip (real compiled service, real 83KB file, 19 assertions, then delete
  and reverse-audit) took one script and is the only evidence that the Prisma
  model and the hand-written DDL agree.

## Afterword — 2026-08-26

The session ran a second day. Four things worth keeping that the entry above
could not know:

- **I told Leo prod did not have the code. It had, for 17.5 hours.** I read the
  image SHA off the cluster and matched it against a local `main` ref I had not
  refreshed. Principle 0 violated in its purest form: the tag was external state,
  the ref was memory. The rule that would have caught it: *when you read a SHA
  from the world, fetch before you say what it is.*
- **The pod that parses orders was not the pod I was watching.** Order intake is
  done by the on-prem pod (same deployment name, different cluster); my first
  monitor watched the AKS pod's logs, a line that could never have fired. The DB
  row count is the signal that does not care which pod wrote it — that is now the
  primary.
- **Two more mistakes of one shape: treating a broken command as evidence.**
  `kubectl logs` without `-c` on a two-container pod returned "0 everything",
  which contradicted the DB and was the only reason I looked twice. Then an
  `expect` spawn echo matched the grep pattern it carried, producing a
  self-matching alarm. Both are the same missing step: no sanity assertion on the
  carrier before asserting on the content. "Found 0" is worthless without
  "the carrier had something in it".
- **The wrong root cause reached a Jira ticket.** I asserted a pre-commit guard
  had been inert for months; it had not — I searched for the CI export filenames
  instead of the ones the rule text names. The real defect was narrower and more
  interesting (the guard's targets are gitignored, so it is active in one working
  copy and silent in every worktree — which is exactly how this ticket's three
  env vars slipped through). Corrected in place with the correction left visible,
  and the PR built on the wrong premise was closed rather than patched.

Two derived tickets came out of the post-deploy check: VP-17915 (`:latest` on the
order-parsing pod) — fixed, merged, verified live, Done; and VP-17916 (config
declared in the repo reaches nothing) — open, because it needs a source-of-truth
decision rather than a patch.
