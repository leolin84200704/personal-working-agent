# VP-9299 — result-ready 信的 product_list 換到 getReportStatusListV2

## 起點

Leo 只丟四個字：`VP-9299`。ticket 是 2025-02-27 開的一行字，reporter 已離職，13 則 comment 全是 automation 催 due date，沒有 AC。STM 裡已經有一份 2026-06-06 的批次分析。

## 這次真正學到的事：舊分析的「結論」比「事實」更容易腐爛

2026-06-06 那份分析的**結構判讀全對**（哪個檔案、哪個分支、哪兩個 TemplateModel），只有行號位移。但它的兩個**結論**全錯，而且錯在同一個地方：它把 V1 和 V2 當成兩個資料源，於是推出「Final-only filter 會讓清單變短，要問 PM」。

實際去讀 `LIS-Report` 才發現 V1 handler 內部呼叫的就是 `getReportStatusListsByBarcodeV2`，只是多做一次 `.map(p => p.report_name)`。**V1 是 V2 的投影，不是同級的另一個 API。** 這一條讓「要不要問 PM」整個消失。

教訓：舊 STM 的 file:line 可以當索引，**它的因果結論必須重推**。分析當下沒讀到的上游 repo，兩個月後也還是沒讀到。

## 辯論的真正產出：不是選項比較，是把我自己的事實打掉四條

Leo 質疑我為什麼跳過 WORK-LOOP Step 3 的正反辯論（我引的是 session system prompt 的「未經要求不使用 Agent 工具」，不是 repo 規則——這個來源分歧本身值得記）。他要求辯論後，兩個子 agent 獨立複驗，**一致推翻我當天稍早才寫進 STM 的四條「已查證事實」**：

1. 我說 `cheackRedisNolock` 守著每 sample 一封信 —— 那函式**只讀不寫**，writer 在兩處都被註解掉，gate 是死碼。
2. 我說這是 beta 分支（子集流量）—— `let is_beta = true` 硬寫死，條件恆真，是 100% 流量。
3. 我說 helper 失敗回 null —— 有兩條路徑，外層 catch 沒 return，回 undefined；而且兩支 axios 都沒設 timeout。
4. 我拿 `.env` 當依據 —— 線上值來自 ConfigMap，`dotenv.config()` 不覆寫。

第 4 條是最貴的一條：照著它去查 `kubectl -n setting get cm`，才發現 **prod `envm = "prod"` 不是 `stprod`**，而 `createConsumer` 的 else 分支把 `sessionTimeout` 硬寫 45000、完全忽略 caller 傳的 950000。原本我打算採用的 V2 helper 最壞會在 `eachMessage` 裡阻塞 10×5s > 45s → rebalance。**辯論的價值不在於選 A 還是 B，而在於它把我推去查一個我根本沒想到要查的地方。**

我自己也在複驗中修正了子 agent：兩方都寫「Kafka 任何重投都會重寄信」，但 `acquireEventLock` 寫的是永久 `trigger_history`（key 含 event_id），同訊息重投擋得住；真正的暴露是同 sample 的多個事件各發一封。**子 agent 的結論也要當假設驗，不能直接轉述給 Leo** —— 我第一次轉述時就漏驗了這條。

## 收斂

Leo 的裁決很乾脆：「今天的目標是只有 ticket 的 scope，你的這些建議超過了 scope，目前不需要，只要 create ticket + assign 給我自己就可以。今天只修這張 ticket 的，但要把辯證記錄下來，未來可以省下更多時間。」

於是辯論挖出的三個缺陷變成 VP-17753/17754/17755，code 改動壓到只換 URL + 換 mapping。而且因為辯論已經證明了 helper 的 cache 與 retry 都是風險，**最小改動反而同時是最安全的改動**——續用 `getRequest`、續用同一顆 token（實測對 V2 回 200）、連失敗時 throw 的舊行為都刻意保留。
