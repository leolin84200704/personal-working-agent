# VP-17631 — OBR panel labels wrong (Athena, accession 2606306595)

## Origin

## 診斷鏈（class A 變 class C/D）
1. `result_transmission_records` sample 2587879 只有一筆（`cmrqtbfmu001hz307n5fztrzu`，2026-07-18 20:21，
   TRANSMITTED、無 error）→ **投遞是健康的，錯的是內容的 OBR 標籤**。存下的 HL7 有 5 個 OBR：
   `VAREQUISTION10001^Healthspan Assessment Panel`(74 OBX) / `VAREQUISTION94^Other Markers`(1) /
   `VAREQUISTION460^Cardio Zoomer`(5) / `VAREQUISTION471^Foundation Zoomer`(2) / `VAPDF`。
2. `getOrderPackageAndTest?sample_id=2587879` 現在回 `package_id_list [97,51,103,59]`
   （CMP / Beta Cell Function / Lipids / CBC w-diff）+ 22 個 single test = 診所說的 core workup，
   完全沒有 Healthspan / Cardio Zoomer / Foundation Zoomer。
3. `TestPanelMappingService.groupTestsByPanels()` 把 primary path（order API）的**任何**失敗 catch 掉，
   改用 legacy `testIdToEmrCodeMap`：每個 test 指派給 `getPackage2TestMapping` 中**第一個**含它的 group。
   而 **group 10001（Healthspan, 117 members）就是該 API 的第一個 textual key** → 幾乎所有常規
   chemistry/CBC/hormone marker 都被蓋成 VAREQUISTION10001，剩下的 calc marker 落到 460/471。
4. **離線重放確認**：用 legacy first-match 算法跑這支 sample 的 82 個 marker，精確重現 7/18 的檔案
   （74 / 1 / 5 / 2）。→ 該檔確實由 fallback 產生。
5. 7/18 全天只有 2 筆有此 signature（20:21:30 與 20:21:36，同診所），其他當天投遞標籤都正確，
   且同 sample 今天 API 正常 → **transient 失敗**（retry 就會對，靜默 fallback 不會）。

## [2026-08-06 23:1x] 未歸屬 marker 的歸屬規則 — 從 PDF 反推成功（Leo 提的方向）

### 取得 PDF 的路徑
DB 的 `generated_hl7_content` 把 PDF 剝成 `[PDF_CONTENT_REMOVED_FOR_DB_STORAGE]`，但**磁碟上的實體檔有**：
`result_transmission_records.file_path` → PV `emr-pv-storage:/EMR_storage/HL7Result_prod/{record_id}/{accession}.hl7`，
VAPDF OBX 的 field 5 = `^AP^^Base64^<data>`，base64 decode 即得 PDF；`pdftotext -layout` 轉文字看分節。
（順帶：prod 現在跑 `4828871`，#329 已上線，dry-run `send_result=false` 可用 —— 實測 success:true。
但 dry-run **會沿用既有 record 並更新 generation 欄位**（file_size_bytes/updated_at 被改），不是零副作用。）

### 報告的分節 = report team 的 catalogue
`LIS-Report/all_report_tests.json`（15,963 筆）每筆 = `{testId, productType, category, ...}`。
用 productType ∈ {Vibrant America, VA Internal}（= classic VA 報告）取 `category`，**與 PDF 實際渲染完全一致**
（sample 2500872 實測：Iron/UIBC/TIBC/TS 在 "Anemia" 節、Testo/SHBG/FAI 在 "Hormones (all)"、HOMA IR 在 "Insulin Resistance"）。

而這些 category 名稱**正好是 price mapping 裡 GROUP 的 name**，可直接換成既有 EMR code：

| marker | 報告 category | EMR code |
|---|---|---|
| Testosterone Total / SHBG / Free Testosterone | Hormones (all) | VAREQUISTION57 |
| Iron / TIBC / UIBC / Transferrin Saturation | Anemia | VAREQUISTION36 |
| HOMA IR | Insulin Resistance | VAREQUISTION69 |
| Free PSA (FPSAP) | Other Markers | VAREQUISTION94 |
| Non-HDL-C / TC-HDL / HDL-TG / TG-VLDL / Reynolds / Framingham / Extra Score 1&2 | 無 VA-report category（只存在於 Zoomer productType 內） | → VAREQUISTION94 Other Markers |

**否證過的替代規則**：「取最小的包含套組」不對 —— 它會把 Iron 群歸到 `TIBC [Incl. UIBC and Iron]`(39003)、
Testo 群歸到 `Testo, Free [Incl...]`(39001)，都與報告的 Anemia / Hormones (all) 不符。報告用的是自己策展的 category，
不是套組成員關係。

## 上游（order API）失敗後的實際處理鏈（查證後）
- `ensureResultTransmissionRecord` 在 `generateHl7Content` **之前**（main line 205 vs 217）→ 我新加的 throw
  一定有 DB 痕跡：record 被標 `GENERATION_ERROR` + error_message + `retry_count++` + `next_retry_at`。
- BullMQ：`attempts: 5`、exponential backoff base 120s（≈ 2/4/8/16 分，總窗約 30 分）。processor catch → `markGenerationFailure` → re-throw → retry。
- 5 次用盡：`onFailed` → `markPermanentFailure` → `GENERATION_ERROR` + `TRANSMISSION_ERROR` +
  `PERMANENT FAILURE after max retries`，**`next_retry_at = null`**。
- **缺口**：`TIMEOUT_RETRY`（VP-17343）只在請求層 timeout 時觸發，**沒有掃 `next_retry_at` 的 cron**；
  emr-v2 的 @Cron 只有 order fetch / mapping cache / scheduled reports。agent 端 DailyJob 也只看 order 側（hl7_fail）。
  → 超過 30 分的上游中斷 = 報告不會送出、且**沒有人在看** ERROR row。修復把「靜默錯誤」換成「明確失敗但無人監看」。

## 可蒸餾到 LTM 的 pattern
- **「投遞成功」不等於「內容正確」**：result 類 triage 過去都停在 transmission_status；這次錯在 OBR 標籤，
