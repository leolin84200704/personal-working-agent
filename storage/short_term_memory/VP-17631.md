# VP-17631 — OBR panel labels wrong (Athena, accession 2606306595)

## Origin
Leo 轉來 Athena 診所（clinic 137932）抱怨：accession **2606306595**（patient SNEHAL PATEL, F, 1985-10-23,
sample_id 2587879, order 11436624, customer 41125）。診所只訂了 standard core panel，但 Athena 裡顯示
Healthspan Assessment Panel / Cardio Zoomer / Foundational Zoomer，點進 hyperlink 的 result 跟 panel 名稱不符，
診所懷疑是不是別的病人的結果。

## 診斷鏈（class A 變 class C/D）
1. `result_transmission_records` sample 2587879 只有一筆（`cmrqtbfmu001hz307n5fztrzu`，2026-07-18 20:21，
   TRANSMITTED、無 error）→ **投遞是健康的，錯的是內容的 OBR 標籤**。存下的 HL7 有 5 個 OBR：
   `VAREQUISTION10001^Healthspan Assessment Panel`(74 OBX) / `VAREQUISTION94^Other Markers`(1) /
   `VAREQUISTION460^Cardio Zoomer`(5) / `VAREQUISTION471^Foundation Zoomer`(2) / `VAPDF`。
2. `getOrderPackageAndTest?sample_id=2587879` 現在回 `package_id_list [97,51,103,59]`
   （CMP / Beta Cell Function / Lipids / CBC w-diff）+ 22 個 single test = 診所說的 core workup，
   完全沒有 Healthspan / Cardio Zoomer / Foundation Zoomer。
3. `TestPanelMappingService.groupTestsByPanels()` 把 primary path（order API）的**任何**失敗 catch 掉，
   改用 legacy `testIdToEmrCodeMap`：每個 test 指派給 `getPackage2TestMapping` 中**第一個**含它的 group。
   而 **group 10001（Healthspan, 117 members）就是該 API 的第一個 textual key** → 幾乎所有常規
   chemistry/CBC/hormone marker 都被蓋成 VAREQUISTION10001，剩下的 calc marker 落到 460/471。
4. **離線重放確認**：用 legacy first-match 算法跑這支 sample 的 82 個 marker，精確重現 7/18 的檔案
   （74 / 1 / 5 / 2）。→ 該檔確實由 fallback 產生。
5. 7/18 全天只有 2 筆有此 signature（20:21:30 與 20:21:36，同診所），其他當天投遞標籤都正確，
   且同 sample 今天 API 正常 → **transient 失敗**（retry 就會對，靜默 fallback 不會）。

## Prod 影響（下限）
`generated_hl7_content LIKE '%VAREQUISTION10001^Healthspan%'` 共 34 筆，逐筆對 order API 檢查
`10001 ∈ package_id_list`，**12 筆是誤標**（2026-01-05 → 07-18，跨 ATHENA/MDHQ/OPTIMANTRA/PF）：
samples 2400777, 2436807, 2220757, 2467814, 2482236, 2489991, 2501407, 2559894, 2500872, 2567900,
2597130, 2587879。這是**下限** — 同一 fallback 也會誤標到其他 superset package，此查詢抓不到。

## 附帶發現
1. **靜默丟資料**：primary path 只為 order API 回報的 package/single test 產生 OBR，
   result set 中未被歸屬的 marker 直接消失、零 log。重推後 2587879 從 82 → 71 marker，
   掉的 11 個是 Testosterone Total(14.3) / SHBG(44.6) / Free Testosterone(0.21) / HOMA-IR
   + 5 個 Cardio Zoomer ratio/score + 2 個 FZ Extra Score。前三個是真實 assay，屬 package 39001
   `Testo, Free [Incl. Total, Albumin, SHBG]`，order API 沒把它列給這支 sample。
   PDF report 仍含全部結果，所以 clinician 不是全盲，但 discrete OBX 少了。歸屬政策需 product 決定。
2. **prod dry-run 不可用**：`send_result=false` 走 `getClientConfiguration()` → 查
   `prisma.emrResultCustomer`，prod `lis_emr` **沒有 `emr_result_customers` 這張表** → 直接失敗。
   只有 send path 能跑（它從 ehr_integrations row 組 client config）。所以無法先預覽再投遞。

## 修復（PR #326 draft → staging）
https://github.com/Vibrant-America/lis-backend-emr-v2/pull/326
- order API transport/HTTP/timeout 失敗 → **throw**（`[OBR_GROUPING_FAILED]`），讓 job retry 而不是猜標籤
- `200` 但 0 package + 0 single test 也 throw（`[OBR_GROUPING_EMPTY]`）— 回空 panels 會產生無 OBX 的 ORU（LIS-7626）
- legacy grouping 保留在 `OBR_LEGACY_GROUPING_FALLBACK`（預設 off）逃生門後，ops 不必 deploy 就能恢復 best-effort 標籤
- 未歸屬 marker 改為 `[OBR_UNATTRIBUTED_RESULTS]` warn 出 test id
- 新 spec `test-panel-mapping.grouping-fallback.spec.ts`；`npx jest src/modules/result` 14 suites / 72 tests 全過；`npm run build` 乾淨

## 可蒸餾到 LTM 的 pattern
- **「投遞成功」不等於「內容正確」**：result 類 triage 過去都停在 transmission_status；這次錯在 OBR 標籤，
  DB 一片綠。診斷 result 內容問題要把 `generated_hl7_content` 跟「order API 說訂了什麼」對撞。
- **fallback 只要語意上是「猜」，就必須 fail loud**：first-match grouping 對 superset package 天生會贏
  （10001 是第一個 key），degradation 產出的是合法但錯誤的臨床文件。與 patterns.md #5/#6/#9 同一族。
- **離線重放 legacy 演算法是便宜的 root-cause 證明**：用兩支 mapping API 的資料重跑舊算法，
  精確重現當時檔案的 OBX 分佈（74/1/5/2），不需要當時的 pod log。
