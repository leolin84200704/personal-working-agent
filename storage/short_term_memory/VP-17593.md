# VP-17593 — booking verification email → Azure notification Event Hub

## Origin
2026-08-04 infra Slack directive: unplug all dependencies on local DB / local Kafka / local Redis
(+ CDC topics 153_* from 60.2) TODAY. Full audit of emr-v2 + transformer found this as the one
user-facing breakage: `AppointmentNotificationEmailService` produced ONLY to on-prem brokers
(`KAFKA_BROKER_carlos*` 60.9/60.10:9095, topic `Notification-Email-Template`), throws on failure,
`public-booking.service.ts:727` surfaces 400 → patients cannot get verification codes.

## Change (PR #551 draft -> stage_test, branch bugfix/leo/VP-17593)
- Producer switched to shared `kafka-azure-notification.client.ts` (vibrant-notification-events
  hub), topic from `Azure_notification_topic` (= notification-email-template). Same hub + IDENTICAL
  Postmark message schema as `EmailService` (proven in prod during VP-16921).
- Lazy `import()` of the client (utility.service pattern — client validates env at import time).
- `allowAutoTopicCreation: false`; message shape + throw semantics unchanged; KafkaModule import
  dropped (no transitive DI consumer — verified public_booking + meeting-request).
- No config change needed: `Azure_kafka_notification_*` already in both ConfigMaps + injected.
- Tests: +4 unit (topic/schema/array recipients/failure/producer reuse) 4/4; tsc 37 pre-existing
  errors before AND after (none in touched files).
