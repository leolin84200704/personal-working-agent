# VP-17868 - Work Loop Record

## Ticket Analysis
- Reporter Zhenhe Zhang, P2, `jira_escalated`, status already Done in Jira (message-clarity follow-up requested by Leo, not a reopen).
- Symptom: provider selects accession 2606186863 in the schedule-consult dialog, gets "The Accession ID selected has been used.", says they have no upcoming consults.
- PM's comment shows the holding row: event 11504, practice 150105, start 2026-07-24 16:00Z, `is_canceled: false`, accession_ids ["2606186863"]. The consult already ran — the provider was right.
- Root confusion: `v2_event_accession_claim` release is wired only to cancel / delete / accession swap (`event.service.ts` L757 / L1120 / L2002 / L2299 / L4932). Nothing releases a claim when the consult happens, so the blocking consult is normally a past one. The message implies a live booking the provider can find.
- Works-as-designed part: 1 accession = 1 consult (VP-16410). Unlock is `resetEventAccession` (admin / clinicadmin / clinicalteam), and its ONLY UI is vibrant-wellness-portal `ScheduleService.js resetSampleStatus` — nothing in va-portal can release a claim, so "contact your clinician" would have been the wrong instruction.

## Approaches Considered
- A (chosen by Leo): name the consult date in the message → needs BE `consultDate` + an ownership gate.
- B: FE-only rewording that says past consults count.
- C: Leo's original draft, corrected for audience.

## Decisions Made
- Option A.
- Date disclosure is gated: `isClaimable` accepts any accession id and never verifies it belongs to the caller's clinic, so an ungated date turns the query into a probe for other practices' bookings. Disclose only when `claimed_by` matches the caller's user id, or the caller is the holding event's creator / a participant (provider calendars in 150105 carry `calendar_owner_id = customer_id`).
- `supportEmail` is passed as an interpolation param, not baked into the message: vue-i18n (v11) reads `@` in a message body as linked-message syntax. Repo has both a raw `Support@vibrant-america.com` value and a `support@@vibrant-america.com` one, i.e. no reliable precedent.
- Dropped the Alert's hard `:height="42"` on this alert only — the longer copy wraps to 2-3 lines and the fixed box clipped it.

## Retrospective
- The message was a symptom; the durable question is whether a completed consult should keep consuming its accession. Current answer is yes (VP-16410 intent), which makes this a product rule that has to be *stated* in the UI rather than a bug to fix.
- Checking who can actually perform the remedy before writing "contact X" caught a wrong instruction in Leo's draft: the audience of the message IS the clinician.

## Lessons Learned
- Before writing "contact X to fix this" into an error message, find the code path that performs the fix and confirm which role and which UI owns it. The unlock here lives in a different portal than the error.
- An error message that says a resource is "in use" must name the thing using it, or say that finished/past uses still count — otherwise the user searches their live list, finds nothing, and escalates.
- Check write access to a repo before planning work in it: `gh api repos/{owner}/{repo} --jq .permissions.push`. A cross-repo fix can be half-deliverable.
