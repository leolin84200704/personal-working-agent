# VP-17759 — which address should receive the consult confirmation

## The booking (ground truth, calendar_prod)

`v2_event` **12801**, practice 150105 (clinician practice), `create_time 2026-08-16T20:22:04Z`
— 12 seconds before the email in the ticket (17:22:16 GMT-3 = 20:22:16Z).

```
event_title  Provider Consult- 30 Minutes
event_type   Clinical Consult
start_time   2026-08-19T13:00:00Z   (= 06:00 America/Los_Angeles, matches the email)
creator_calendar_id 36318
notes  [Accession Id 2607106245: Total Immunoglobulins (Free Add-On), Candida + IBS Profile]
       [Name: Nikol Hopkins] [Phone: 312-535-7345]
       [Email: nikol.hopkins.dn@mdlifespan.com] [Meeting Type: Call]
```

Participants: Dana Filatova's Clinician Calendar (30794, clinicadmin) + PAUL SAVAGE's calendar
(36318, role `patient`, `calendar_owner_email = admin@mdlifespan.com`).

## Diagnosis chain

1. **The typed email is stored as free text in `v2_event.notes`.** It sits inside the same
   bracketed string as Name / Phone / Meeting Type, which is display context for the clinician.
   Nothing reads it back out as a recipient — grepped the whole calendar module.
2. **The email in the ticket is Postmark 33802988** = `appointment_scheduled_by_provider` /
   `patient` in `email-templates-clinician.yaml`. Its field list
   (`clinical_team_member_name`, `consult_date`, `consult_time`, `consult_team_member_email`,
   `consult_team_meeting_type`, `meeting_location`) matches the received body exactly.
3. **Its recipient is the calendar address**: `event.service.ts`
   `sendAppointmentScheduledEmailForCreateEvent` → `to: patientCalendar.calendar_owner_email`,
   where patientCalendar is the participant whose `v2_calendar.role = 'patient'` (in the
   clinician flow that is the booking provider). Here: `admin@mdlifespan.com`.
4. **Nothing downstream rewrites it.** notification-center passes the message through —
   `consumer.service.ts` builds the Postmark payload with `To: job.data['To']`.
5. **Independent corroboration**: `v2_reminder_audit_log` for event 12801 has both reminders
   (48h `sent_at 2026-08-17T13:00:00Z`, 24h `2026-08-18T13:00:01Z`, template 33802989) with
   `recipient_email = admin@mdlifespan.com`, `status = sent`.

## Refuted along the way

- *The calendar address was changed after the send* — calendar 36318 has
  `created_at = updated_at = 2026-02-24T21:13:27Z`. Never touched.
- *An account notification email is looked up for this template* — there is no such lookup in
  the path; the recipient is the calendar column.
- *`paul.savage.md@mdlifespan.com` is stored somewhere in ours* — it appears in **no**
  `v2_calendar` row, no `v2_reminder_audit_log` row, and no `email_send_out_request` row. The
  only mdlifespan addresses we hold are `admin@`, `tim.savage@`, `clientliaison.tim.savage@`.

So the `To:` header the customer quoted is not an address our system can produce. The remaining
explanations are practice-side mail routing (`admin@` aliasing into Paul Savage's mailbox) or
support transcribing the recipient's own mailbox instead of the header — worth one question to
the requester, not a code hunt.

## Answer to the ticket's question

The manually entered address is ignored **by construction, not by accident**. It is captured as
contact text for the clinician; the recipient is always the booking account's calendar address.
So the current behaviour is "working as coded" — whether it is working *as intended* is the
product decision the ticket is really asking for.

## Recommendation (for the PM answer)

Keep the calendar/account address as the authoritative recipient, and treat the form field as
what it currently is — contact info for the clinician — fixing the UI wording so it stops
implying the confirmation goes there.

Reason, from this same data: the field is unvalidated free text and already wrong twice. The DB
holds `nikol.hopkins.dn@mdlifespan.com` while the ticket quotes `nikol.hopkins.nd@` (transposed),
and the sibling booking event 12802 (created 2026-08-16T20:23:57Z) holds
`nikol.hopkins.dn@mdifespan.com` — a domain typo. Routing appointment details to a typed string
would have bounced both times, silently.

If the customer does need that person notified, the safe shape is an **additional** validated
recipient, not a replacement, and it has to cover reminders too (they go to the same address —
see the audit log above), otherwise confirmation and reminders would diverge.

## Reusable

- The clinical-consult booking form's Name / Phone / Email / Meeting Type all land in one
  bracketed free-text string in `v2_event.notes`. Anything asking "why didn't we use what the
  user typed" in this flow ends there.
- `v2_reminder_audit_log.recipient_email` is the cheapest proof of who we actually emailed for a
  calendar event — it is written per send with an idempotency key and status.
- The clinician practice (150105) has its own template registry
  (`email-templates-clinician.yaml`); template ids and field names differ from the standard
  patient/provider set, so grep by Postmark template id when tracing a received email.
