## Ticket Analysis

**Goal（目的）**：當整合中介層收到無法辨識 provider 的 HL7 order 時，不再只 log 丟棄，而是把整封原始 HL7 完整寫進新的 quarantined_orders 表（永不遺失訊息），由 UniMod admin 審核 resolve（link 既有 provider / 建新 provider / reject）。配合 7 天自動過期（含 48hr 警示信）與 dead-letter dual-write 做災難復原。本票是 PRD EHR Integration Enhancements V2 (pageId 2316173315) Feature 1 的 quarantine 後半段。

採「最小可獨立交付片（方案 A）」，但須先等 Leo/Kristine 確認 cutover 時程才動工（見 blockerReason）。

### 風險與邊界案例
- AC2 non-blocking 的真正風險：fire-and-forget 必須確保 quarantineService.write 內部任何 throw（DB 連線失敗、TEXT 過長）都被 .catch 吞掉，否則 unhandled rejection 或誤 propagate 回 worker 會重蹈 VP-16463 的 fail-out。驗證要實際模擬 DB 寫入失敗，確認 worker 仍把 order fall-through 成功。
- AC3 raw HL7 完整儲存：raw_hl7_message 須 TEXT/LONGTEXT，不可截斷；要測超大 HL7（多 OBR/OBX）不被 MySQL 預設欄位長度截掉，且驗證 round-trip 內容逐 byte 相同（PHI 完整性）。
- Prisma enum 慣例不一致（已查證）：engineer 與 VP-16164 STM 都聲稱 schema 無 prisma enum，實際有 35 個且 EHR-V2 新表用真 enum — 此為對 engineer 分析的明確修正。
- queue 技術：AC6 dead-letter 的 intake 是 BullMQ+Redis（process-hl7-file queue）非 Kafka；DLQ 若用 BullMQ failed-job 機制 vs 另建表，行為差異大，不可假設。
- 重複 quarantine：同一封 HL7 重送（remote delete 失敗或 re-enqueue）可能重複寫入 → 需以 order_id 或 hl7_file_input id 做 dedupe/unique，否則 admin queue 充斥重複。
- expiry cron 多 pod 競態：intake pod 可能多副本，@Cron 在每個 pod 都跑會重複寄 48hr 信/重複 expire → 需確認 cron 只在單一 pod 跑（比照 scheduled-reports 的 pod gating）。
- 48hr 警示信收件人：AC5 「assigned admin or default group」未指定 default group 是誰，未定義會靜默不寄。
- matched_practice_id/provisional_provider_id FK 指向 VP-16164/VP-16168 的表，這兩票 read-path 尚未切/表尚未建 → 本票先存 nullable 值不加硬 FK constraint 以免 cross-ticket 卡住。

**Code reality correction to the 06-06 entry.** The hook point named there (processor line 76-87 →
now `hl7-order.processor.ts:130-156`) is **only an advisory log** since VP-16968/VP-17533: it resolves
the VP-16832 ordering-provider email and is wrapped in a catch that must never fail the order. The
authoritative miss is `parseResult.result.customer_not_found` → `markCustomerNotFound()`
(`:190-193`, `:504-518`) → `markFailure()` → retry_num-- , `parse_finished` stays 0, `last_error`
written, and at retry_num=0 `logRetryExhausted()` fires `[RETRY-EXHAUSTED]` + a Sentry→Slack alert
(VP-17544). So the PRD premise "hard-fails with developer intervention required" is already half
false: the order retries, is traced, and alerts. What is still missing is exactly (a) durable raw
payload, (b) a non-engineer resolution surface, (c) an auditable count.

**Lesson injection (Step 1.4, k=2 from framework/ENGINEERING-LESSONS.md):**
- *"`void somePromise()` 丟棄的是回傳值，不是 rejection"* — governs AC2 verbatim: an unawaited
  quarantine write with no `.catch()` is an unhandled rejection, and modern Node ends the process, so
  a best-effort side-branch becomes the thing that kills order intake. Every fire-and-forget needs an
  explicit `.catch()` **plus** an outer try/catch for synchronous throws (DI gave undefined), and the
  "failure does not break the main flow" test must use a real `mockRejectedValue`, not a sync throw.
- *"Diagnosis in the agent layer, facts in the app"* — quarantined_orders stores bare facts + raw
  payload only. Root-cause text belongs in the existing VP-17412 `error_detail` agent path; do not
  build a diagnosis engine into the service.

**Multi-pod cron gating exists already**: `hl7-order-fetch.service.ts:117-168` uses
`redlock.acquire(LOCK_KEY)` + extend + force-release. But VP-17422's incident (redis NOPERM →
fail-open lock → 3 replicas each sent the daily report) says a redis lock must not be the only
guard on an outbound email; per-row `warning_sent_at` claimed by a conditional UPDATE is the
idempotent form.

**關鍵設計決定（與 06-06 分析不同者）**
1. **hook 點是 `alertOrderNotPlaced`**，不是 06-06 說的 resolveIntegration else 分支（那條現在只是
   advisory log）。這個點同時被 `logRetryExhausted`（retry 用盡）與 `markTerminalFailure`（首次即
   terminal）呼叫 = 「被放棄」的唯一定義，於是 quarantine 與 VP-17544 的 Slack 告警描述同一組單。
2. **捕捉所有 failure class，不只 identity**。PRD 只設 `unknown_provider` / `unknown_origin`，
   但 abandonment hook 對 emr_code_not_found 等一樣會觸發，而那些單的 raw HL7 同樣會消失。
   加第三個 enum 值 `OTHER_FAILURE`，而不是丟掉或誤標成 identity 問題。
3. **`final_outcome` 與 `quarantine_reason` 分離**：provider 有 match、只是後面才失敗的單記
   `final_outcome=ROUTED` + `reason=OTHER_FAILURE`。兩者合併會讓「provider 解析失敗率」
   這個本表唯一存在理由的數字失真。
4. **step 2/3 記 SKIPPED 不記 NO_MATCH**——emr-v2 沒實作那兩步，把沒跑過的查詢記成 no-match
   會直接污染要量的指標。
5. **raw HL7 從磁碟讀**（`archieve_file_path` → `localDir/file_name`），不從呼叫端 thread 進來：
   markFailure 有多個 call site，其中外層 catch 拿不到 raw。讀不到檔就寫 `raw_capture_error`
   仍建 row（身分事實沒了，但至少證明這張單存在過且被放棄）。
6. **expiry cron 不用 redis lock**：兩個 UPDATE 的守衛都在 WHERE（`status=OPEN`、
   `warning_notified_at IS NULL`），多 pod 併發 = no-op。VP-17422 就是 redis lock fail-open
   讓 3 個 replica 各寄一份日報；條件式 UPDATE 不可能 fail open。
7. **每個 varchar 欄位進 DB 前 truncate**：一個超長 vendor 欄位讓 INSERT 爆掉的話，
   這張為了保存訊息而存在的表反而會弄丟訊息。`raw_hl7_message` 是 LONGTEXT，絕不截斷。
