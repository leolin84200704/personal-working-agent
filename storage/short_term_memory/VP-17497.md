# VP-17497 — Order Intake API: reclaim placerId after terminal failure

## Ticket Analysis

### [2026-07-27] Origin: Slack (Tianhao Wang, api-product, posted 07-22)
- Sandbox POST /v1/orders placerId PORTAL-3226427-GUT_ZOOMER -> 201 {status:duplicate, sampleId:null}; doc says resend returns original result. New patient order placed fine.
- Ground truth (staging order_intake id=62): status=ineligible, error=IncompletePatientInfo, created 2026-07-22 20:23 UTC, sample_id null. Every resend short-circuited to duplicate/null.
- Root cause: unique-insert-first idempotency (order-intake.service.ts P2002 branch) returned duplicate for ANY existing row status. Known wrinkle from VP-17286 E2E scope item 7 — follow-up never scheduled. Code comment "caller gets a 5xx to retry on" contradicted itself.
- Leo's design intent: terminal failure must NOT consume the placer id; resend must re-check (e.g. profile completed after IncompletePatientInfo).

## Decisions Made

- [2026-07-27] Leo: Phase 1 (reclaim, no schema) + Phase 2 (failed retryable via stored payment) together, separate commits; docs too.
- Reclaim keeps the row (audit trail) — status-gated atomic updateMany, NOT delete; concurrent resends: exactly one wins.
- failed is dangerous to blindly retry: finalize is charge-first -> a placement failure may strand a completed charge; order_intake had no payment columns to replay. Phase 2 persists the charge immediately after transactionPay returns (before placement outcome known) and passes it through parseOrderInfo so finalize's pre-existing HL7 replay branch (sample_id_payment != null) skips the charge.
- Same placerId must carry the same order payload (documented); payload replaced on reclaim.
