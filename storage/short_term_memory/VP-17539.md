# VP-17539 — legacy bundle → component test split before BestDeal

> Created by the 2026-07-31 dream closeout audit. Leo transitioned this to Done on 2026-07-30 11:53 PT
> with **no STM file, no Jira comment, and no PR carrying the VP-17539 id** — this file exists so the
> ticket has a record and so the unmet acceptance criterion is not lost.

## What the ticket asks

Six legacy "Zoomer + Genetics" official bundles are absent from BestDeal's `allTests`, so passing the
bundle id to `GetBestDealSuggestion` returns `non_existing_discount_panel_ids`. Fix = split the bundle
into its two component test ids and price the components. Explicitly: **only the bundle→test-id mapping
may be hardcoded, never a price** — BestDeal stays the single source of pricing truth (prices drift,
and components can combine with other ordered tests into different deals).

| Bundle | Components |
|---|---|
| 18006 Cardio Zoomer + Cardio Genetics | 842, 843 |
| 18015 Toxin Zoomer + Toxin Genetics | 844, 724 |
| 18016 Oxidative Stress + Anti-oxidant Genetics | 823, 822 |
| 18017 Cellular Zoomer + Anti-oxidant Genetics | 854, 822 |
| 18018 Nutrient Zoomer + Nutrient Genetics | 849, 856 |
| 18019 Foundation Zoomer + Methylation Genetics | 853, 851 |

## Where the code actually came from

No PR was ever opened under this id. The implementation shipped as **VP-17535 / PR #301**
(`staging` 2026-07-29 23:00Z → promotion #302 → `main`, deploy `success`), i.e. the ticket Leo had
framed as the **TEMPORARY** workaround. See [[HL7FAIL-20260729-PLESSEN]] for how it was designed
(Leo rejected a synthetic fixed-price response twice before landing on the component split).

Verified on prod tonight by dist grep (`order-test-client.service.js`): all six pairs present and
**identical to the ticket's table**. Response passes through untouched → no hardcoded price. So
acceptance criteria 1 and 2 are satisfied against ground truth.

## Open — two things the closure did not settle

1. **Acceptance criterion 3 is unmet.** It requires placing one order per bundle (all six) and
   confirming the BestDeal price matches the expected bundle price. Actual evidence: only **18019** is
   proven end-to-end in prod (hl7_file_input 6735 → sample 2605735, order items 853+851, total $1300),
   plus a bare BestDeal probe for 18015 (`[844,724]` → 200) and 18019 (`[853,851]` → 200 $700). The
   other four bundles (18006, 18016, 18017, 18018) have never had an order placed. 18016/18017 share
   component 822, which is exactly where the dedupe logic could go wrong — and that path is untested
   live.
2. **"Done" contradicts the code's own labelling.** The shipped code still carries
   `VP-17535 — TEMPORARY`, the runtime log emits `[VP-17535 TEMPORARY] BestDeal panel(s) … split into
   component tests`, and VP-17535 remains `Dev To Do` as the removal tracker whose condition is
   "DELETE this fallback once BestDeal returns 200 for 18019". But VP-17539's whole premise is that
   the split **is** the permanent design. Both cannot be true: either VP-17539 is Done and the
   TEMPORARY markers + removal condition must go, or the split is still interim and VP-17539 is not
   Done. Leo to pick one — otherwise a future reader deletes production pricing behavior by following
   VP-17535's instructions.
