## Approaches Considered

### [2026-07-31] Root cause
`AccessionClaimService.resetAccession` (`accession-claim.service.ts:177`) deletes the claim row unconditionally — it never inspects the holding event. `resetEventAccession` resolver (`accession-claim.resolver.ts:56`) only gates on role (admin/clinicadmin/clinicalteam, per calendar-clinicalteam-reset-accession). So "free the accession" and "the appointment still exists" are allowed to coexist. Booking-side (`createEvent` :514, `createEventByPatient` :1757) trusts the claim table exclusively.

### Options
- **A (recommended, primary): block reset when the holding event is active AND start_time > now()** — error telling staff to cancel/reschedule the upcoming appointment first (cancelling auto-releases the claim via `released_by_event`, so no reset is even needed afterwards). Leaves the 222-use past-consult follow-up flow untouched. Optional `force` flag if ops needs an escape hatch.
- **B: cascade-cancel the held future event on reset** — destructive (cancels a real appointment + fires cancellation emails/Kafka) and hides intent; not recommended as default.
- **C (defence in depth): at booking time reject when another ACTIVE FUTURE event already carries the accession**, independent of the claim table. Must be scoped to FUTURE events only — a live PAST event with a freed accession is the intended post-reset state, so an unscoped check would break the legitimate follow-up flow. Closes residual holes (e.g. accession reset while past, then the event rescheduled into the future → future event with no claim).
- **Data cleanup**: the 2 outstanding accessions need one of each pair cancelled. Which one is a PM/ops call (patient-facing appointment).

## Lessons Learned
- VP-16410's uniqueness guard is sound; the hole is in the RELEASE path, not the claim path. When a feature ships a "reset/override" escape hatch, the escape hatch needs its own precondition check — otherwise ops turns it into a routine tool (245 uses in 3 months) and it silently becomes the primary way the invariant gets broken.
- Reporter statements about "nobody did X" must be checked against the audit table before being taken as the starting premise — here the audit log named the resetter and the timestamp within one query.
