# VP-17524 - Work Loop Record

## Ticket Analysis

Jira: https://vibrantamerica.atlassian.net/browse/VP-17524 — Bug, P2, Dev To Do, reporter+assignee Leo.
Self-filed by the nightly dream scan on 2026-07-28; no comments, no links.

### Confirmed in prod (2026-08-06, pod `lis-emr-v2-deployment-prod-7dc786b5c5-jsnz2`, 15h window)
- 1650 `ResultStatusMapperService` mapping calls; value distribution:
  `RESULT_NORMAL_M` 698 / `RESULT_HIGH_ABNORMAL_M` 85 / `RESULT_LOW_ABNORMAL_M` 20 /
  `RESULT_HIGH_MODERATE_ABNORMAL_M` 16 / `TEST_NOT_PERFORMED` 2 / **`OUT_OF_RESULT_NORMAL` 2** /
  `RESULT_LOW_MODERATE_ABNORMAL_M` 1.
- Both errors are the only ERROR lines in the whole window. Concrete case captured:
  `Test 76 (EGFR)`, masterlistId 2257, `rawResult=93.41`, `latestTestValue=">90"`,
  displayed range `60-90`, `resultStatus="OUT_OF_RESULT_NORMAL"` -> `abnormalFlag="TNP"`.
- Note `OUT_OF_RESULT_NORMAL` arrives WITHOUT the `_M` suffix every other tag carries.

### Delivered-HL7 impact — ticket's claim needs correcting
The ticket says OBX-8 carries `TNP`. It does not. `hl7-encoder.service.ts:439,596` render
`abnormalFlag === 'TNP' ? '' : abnormalFlag`, so OBX-8 goes out **blank**. The real damage is
`hl7-encoder.service.ts:181-183`: `abnormalFlag === 'TNP'` appends an
**`NTE|...|Test Not Processed`** segment. So a valid normal EGFR is delivered to the EMR with no
abnormal flag plus an explicit "Test Not Processed" note.

### Root cause
`src/modules/hl7/services/result-status-mapper.service.ts` `mapReferenceTypeToStatus()` enumerates
only the tag values someone had already observed. emr-v2 trusts the **pre-computed `resultStatus`
from gRPC** (`sample-test-result.service.ts:397`), whose vocabulary includes report-style
`OUT_OF_RESULT_*` tags. Legacy Java never saw those tags at all — `MasterListClass
.parseResult2SampleTestStatus()` (EMR-Backend `src/main/java/com/vibrant/models/MasterListClass.java:220`)
recomputes the class locally from the value vs the range list. So the switch's `default:` branch
(`RESULT_UNKNOWN_ERROR`) swallows a whole family of legitimate tags.

### Semantics of OUT_OF_RESULT_* — cross-repo evidence
- Producer: LIS-Report `base-report-server/src/result/report-common/util.ts:2234-2244` —
  sentinel value `-999999`/`999999` (below/above reportable range) plus an open-ended normal
  range (`≤X` / `≥X`) yields `OUT_OF_RESULT_NORMAL_M`; otherwise
  `OUT_OF_RESULT_LOW_ABNORMAL_M` / `OUT_OF_RESULT_HIGH_ABNORMAL_M`.
- Consumer 1: LIS-Report `result-tt/result-common/result-common.service.ts:283-287` groups
  `OUT_OF_RESULT_NORMAL` with `RESULT_NORMAL` (no interpretive comment attached).
- Consumer 2: report-pdf `src/service/ReportService/FoodSummaryService.js:22,29` groups
  `OUT_OF_RESULT_HIGH_ABNORMAL_M` with `RESULT_HIGH_ABNORMAL_M`.
=> Org-wide convention: the `OUT_OF_` prefix only means "value fell outside the reportable range";
the clinical class is the `RESULT_*` remainder. That is exactly how the one already-handled case
(`OUT_OF_RESULT_HIGH_ABNORMAL` -> `H`, mapper line 117) was patched in.

### Legacy Java parity for the observed case — answers the ticket's open question
Java `parseResult2SampleTestStatus(">90")` does `Double.parseDouble(testResult.replaceAll("<|>",""))`
= 90.0, matches normal range 60~90 (`<=max && >=min`), returns `RESULT_IN_RANGE` -> "In Range" -> **`N`**.
So legacy Java delivered `N` for this exact EGFR result. The fix restores Java parity; it does not
invent new behavior. No lab/report-team confirmation needed for the NORMAL case.

## Approaches Considered

**A. Minimal (ticket's own proposal)** — add `case 'OUT_OF_RESULT_NORMAL': return 'RESULT_IN_RANGE';`
- Pro: smallest blast radius, exactly what prod proves is broken.
- Con: leaves `OUT_OF_RESULT_LOW_ABNORMAL` (a real producer output, util.ts:2237) mis-delivered, and
  repeats the enumerate-only-what-we-saw anti-pattern that caused the bug.

**B. Systematic (recommended)** — strip the leading `OUT_OF_` in `normalizeReferenceRangeType()` so
every `OUT_OF_*` tag falls through to its base class; drop the now-redundant explicit
`OUT_OF_RESULT_HIGH_ABNORMAL` case label.
- `OUT_OF_RESULT_NORMAL` -> `RESULT_NORMAL` -> `RESULT_IN_RANGE` -> `N` (fixed)
- `OUT_OF_RESULT_HIGH_ABNORMAL` -> `RESULT_HIGH_ABNORMAL` -> `H` (unchanged from today)
- `OUT_OF_RESULT_LOW_ABNORMAL` -> `RESULT_LOW_ABNORMAL` -> `L` (fixed pre-emptively)
- Blast radius bounded: only strings starting with `OUT_OF_`, all of which except
  `OUT_OF_RESULT_HIGH_ABNORMAL` currently hit the error default.
- Naming check: base tags are `RESULT_NORMAL` / `RESULT_HIGH_ABNORMAL`, so the prefix is `OUT_OF_`,
  not `OUT_OF_RESULT_`.

**C. Change the `default:` branch to something softer than `RESULT_UNKNOWN_ERROR`** — rejected.
Failing closed on a genuinely unknown tag (and keeping the ERROR log as the tripwire that found this
bug) is correct. Out of scope.

Both A and B keep the `default:` ERROR log intact.

## Retrospective

**假設 vs 結果.** The initial analysis predicted the fix and the semantics correctly, but got the
delivered symptom wrong in the same way the ticket did — and the ticket was written by me
(dream scan, 2026-07-28). I had asserted "OBX-8 abnormal flag TNP" from reading the mapper alone.
Following the flag one layer further into `hl7-encoder.service.ts` showed OBX-8 is blanked for TNP
and an `NTE|Test Not Processed` is appended instead. Same severity, different artifact — and the
NTE is the part a clinician actually sees.

**What made this cheap.** Three independent repos (LIS-Report producer, LIS-Report consumer,
report-pdf consumer) already encoded the `OUT_OF_` convention. Finding all three turned a
"go ask the lab team what this type means" ticket into a decided one in a single pass. The ticket's
own proposal said to confirm with lab/report team first; the code was a faster and more reliable
oracle than a human round-trip would have been.

**Java parity as the tiebreaker.** `parseResult2SampleTestStatus(">90")` resolving to `N` was the
single fact that turned "this is probably right" into "this restores previously-correct behavior".
Worth reaching for whenever a service is a port of a legacy one: the old implementation is a
specification you can execute in your head.

**信心度: 4/5.** Independent from diagnosis through E2E; the one thing I would not have done
unprompted is the before/after E2E on live prod data — Leo asked for it, and it is what upgraded
the claim from "tests pass" to "the wire format changes in exactly one place".

## Lessons Learned

**技術面 — a mapping table over a vocabulary you do not own will always be short.** This mapper
enumerated the tag values that had been observed. That is fine while the producer is you; it is a
latent bug when the producer is another team's pipeline. The port from Java changed the contract
without anyone noticing: Java *derived* the class from the value, emr-v2 *trusts a label*. When
that shift happens, prefer structural normalization (strip known modifier prefixes/suffixes, then
match the base) over adding one more `case` each time prod screams. Keep the loud fallback: the
`default:` ERROR log is the only reason this bug was ever visible.

**流程面 — describe the symptom from the artifact, not from the variable.** The internal value was
`TNP`; what went on the wire was a blank field plus an NTE segment. One extra hop of reading changed
the description of the bug. For anything that leaves the process — HL7, an API response, an email,
a file — trace it to the boundary before writing the symptom down.

**工具面 — a read-only "generate content" endpoint is the highest-value thing a delivery pipeline
can expose.** It made a true prod-data E2E possible with no VPN, no deploy, no side effects:
port-forward the upstreams, boot the service in a role that registers no crons and no consumers,
and diff patched vs unpatched over the same inputs. The control samples (which had to come out
byte-identical) were what made the diff evidence instead of anecdote.

**zsh gotcha:** always quote `--include="*.java"` in `grep -r`. Unquoted, zsh fails the whole
command with `no matches found`, which reads exactly like "nothing in the codebase matches".
