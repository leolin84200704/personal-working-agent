5. **Code mechanism** (transformer-v2 origin/main):
   - reminder.service.ts dispatchEventReminder: recipients filter requires
     calendar_owner_email; clinicadmin@150105 excluded by design (VP-16612);
     recipients.length===0 → **silent return, no log, no audit row**.
   - calendar.service.ts createNewCalendar **never persisted calendar_owner_email**
     (not even when the caller supplied it); the field was always caller-optional
     (added cb14eef 2025-11-21).
   - createPatientCalendarForCustomerIfAbsent copy-once from provider calendar
     (VP-17765's mechanism) — copies the NULL.
6. **No owning writer** (corrected after first-pass claim of "callers stopped
   supplying it" — that was inference, and it was wrong). The field has never had
   a writer on the main creation paths: `createNewCalendar` never persisted it
   even when the caller supplied the optional DTO field, and
   `createPatientCalendarForCustomerIfAbsent` only copies the provider-calendar
   template. Populated rows came from two incidental sources:
   (a) `public_booking/public-booking.service.ts` — its payload carries
   patientEmail, so it writes on create AND self-heals NULL rows (07e2ad3,
   2026-03-04 gave public booking its own `getOrCreatePatientCalendar`; the
   consult flow kept the old copy-only one → two divergent implementations of
   the same operation, only one of which knows about email);
   (b) `migration/update-patient-calendar.ts` — a manual backfill script
   referenced by no module or cron (verified: zero refs outside migration/),
   so it only populates when a human runs it.
   **Decay is piecewise per role** as each source dried up: provider/clinicadmin
   100% NULL from 2026-03; patient calendars 92% populated in March, 68% in
   April, 100% NULL from 2026-05.
7. **Blast radius**: 6,402/15,446 (41%) patient-role calendars in 150105 NULL/empty
   email; 30+ future consults within a week have a NULL-email patient participant.
   Confirmations affected too (same field, VP-17765 finding).

## Retrospective / patterns worth promoting

- **Silent-drop audit gap repeats**: result pipeline (kafka listener) and now
  reminder dispatch both drop work with no log/audit row. "0 audit rows + healthy
  audit table" is itself a diagnostic signature — check the filter before the
  transport.
- **Monthly NULL-rate trend query** (count FILTER by to_char month) pinpointed the
  regression window in one query — faster than git archaeology, and it survives
  cross-repo causes (the writer change was in the CALLER, not this repo).
- GetCustomer ignores clinic_id for contact data (live-verified) — useful for any
  cross-practice email resolution in 150105 flows.
- Local transformer .env CORE_RPC_STAGE still points at dead on-prem v1; cloud
  mirror 10.224.0.199:30276 works with OAuth2 client-credentials metadata.
- **Ownerless-field failure mode** (worth LTM): a nullable column whose only
  writers are (i) one request path that happens to carry the value and (ii) a
  manual backfill script decays silently and *piecewise per row-cohort*. The
  monthly NULL-rate-by-role query is the detector; a single aggregate NULL rate
  hides it because different cohorts break at different times.
- **Self-check miss**: VP-17765 (2026-08-18, two days earlier) queried this exact
  column and computed the *mismatch* rate (3,365/15,389) but never the *NULL*
  rate — the other half of the same structure came back as this P2. When
  profiling a suspect column, always count NULL alongside whatever else you
  measure.
