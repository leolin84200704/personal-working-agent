# VP-17594 — setting-update events: Azure Event Hub only

## Origin
Same 2026-08-04 decommission audit as [[VP-17593]]. `setting.service.ts` publishKafkaEvent /
publishNutriprozKafkaEvent dual-published (on-prem `lis-general-events` + Azure
`general-sample-events`) inside ONE try/catch, local leg first.

## Deeper finding than the ticket premise
The Azure leg NEVER worked in prod: it read `Azure_kafka_host_gen` /
`Azure_kafka_connection_string_gen`, which exist in NO ConfigMap (kubectl-verified on both prod
and st). `brokers: []` → `azureProducer.connect()` throws — and that connect sits BEFORE both
sends, so every call aborted the entire publish. These two events have been silently lost on
BOTH legs the whole time (Sentry-only). The decommission just removes the illusion.

## Change (PR #552 draft -> stage_test, branch bugfix/leo/VP-17594)
- New `publishSettingEventToAzure` helper: provisioned shared client
  `kafka-appointment-event.client.ts` (`Azure_kafka_general_events*` — same hub/env appointment
  events use in prod), lazy import, own try/catch + Sentry, disconnect in `finally`.
- Both builders delegate to it; on-prem leg removed; unused `kafkajs` import dropped.
- Topic selection unchanged (general-sample-events / -staging by SERVER_ENVIRONMENT).
- Tests: +4 unit (prod topic / staging topic / nutriproz payload+disconnect / failure swallowed),
  suite 8/8; tsc pre-existing 37 before and after.
