# VP-17691 — Partner API contract gaps (error envelope, aliases, chargeIndicator)

> **This file was reconstructed by the 2026-08-14 dream closeout audit, not by the work
> session.** The ticket shipped and closed without any STM or journal entry — the
> 2026-08-12 dream had already flagged the same gap for this ticket and it was not
> filled. Content below is from the Jira description, the merged PRs, and tonight's
> live prod probe. Treat the design rationale as authoritative (it is Leo's own writeup
> in the ticket); treat anything about *observed runtime behaviour* as unverified.

## Origin

Sandbox review of `POST /orders` by Tianhao Wang, 2026-08-12, after partner Jordan
reported a 500. The two actual 500s from that review are VP-17686 / VP-17685. This
ticket covers the **contract gaps** from the same review, scoped to what emr-v2 owns.

Of eight gaps raised, emr-v2 owns four. The partner surface this service exposes is only
`/v1/orders` and `/v1/orders/cancel`; `/patients`, `/quote`, `/catalog/products` belong
to the API gateway and other services. **Scope discipline worth keeping**: the ownership
table was written into the ticket before any code, so the four not-ours gaps were
handed off rather than absorbed.

## Changes

### 1. Error envelope + request id
A failing call previously returned NestJS defaults (`{message, error, statusCode}` or a
bare `{statusCode:500,message:"Internal server error"}`) — no machine-readable code, no
id. **That is exactly why the partner could only report "it's a 500"**: nothing in the
response identified their request and we had nothing to search on.

Now `{error:{code,message,requestId,details?}}` plus an `x-request-id` header. A
caller-supplied `x-request-id` / `x-correlation-id` is honoured so both sides' logs line
up; otherwise one is minted. Every wrapped failure is logged with that id (5xx at error
with stack, 4xx at warn). A 500 never carries the internal message.

- **Scoped to the two partner-facing controllers, not global** — the other controllers
  have existing internal consumers that parse the current shape.
- **Outcome responses untouched**: a 422 carrying `status: rejected` / `ineligible` is an
  *outcome*, not an error, and never reaches the filter. (Same distinction as
  [[feedback_never_500_for_caller_actionable_failures]].)
- PR #354 followed up: stamp `x-request-id` on **every** partner response, not just
  failures — a success you cannot correlate is the same support problem one call later.

### 2. Field-name trap
`/orders` took snake_case `patient_id` while the sibling quote endpoint took `patientId`,
so a partner coding consistently in either style got a 400 on one of them. `patientId`,
`test_codes`, `ordering_provider_id` are now accepted as **aliases** — aliased rather than
renamed, so documented names stay authoritative and existing integrations are unaffected.

### 3. chargeIndicator accepted without validation
```
chargeMethodFromIndicator(indicator?: string): ChargeMethod {
  return indicator === 'C' ? ChargeMethod.CUSTOMER_PAY : ChargeMethod.PATIENT_PAY_LATER;
}
```
Anything not exactly `'C'` became patientPayLater. A junk value (`'X'`) or, worse, a
lowercase typo (`'c'`) placed the order **silently billed to the patient instead of the
customer**, answering 201 with no indication anything was wrong. Only C/P/I/O or omitted
are accepted now; anything else is 400 `INVALID_CHARGE_INDICATOR` carrying the received
value. The two existing 400s gained codes: `INVALID_PATIENT_ID`, `MISSING_TEST_CODES`.

## Not code defects — documentation only
- **EligibilityFailure is wired** (the review suspected it was not). Staging has real
  `order_intake` rows with `status=ineligible`, `error=IncompletePatientInfo`. The
  confusion: `patient_not_found` is a *rejected* reason from the patient lookup, which
  runs **before** the eligibility check, so it correctly never appears in `failures[]`.
- **`specimenId` / `sampleCollectionTime` are not "reserved for future use"** — the docs
  say leave them unset, but `order-finalizer` writes both to `emr_sample`. Docs stale.
