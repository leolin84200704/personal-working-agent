# LIS-7716 - Work Loop Record

## Ticket Analysis

### [2026-08-26] Intake
- Jira: LIS project (not VP). Status Dev To Do, P2, assignee Leo, reporter Tianhao Wang. Created 2026-08-26.
- Background: Zendesk 746900 (Maristany Medical / Cerbo C2558) — practice lost PERSONALIZED report style when EHR integration re-provisioned via auto-integrate 2026-07-27/28. `report_option` is create-only in emr-v2 API, defaults to CLASSIC when omitted. 17 reports pushed as Classic since 2026-08-04. Only ~3/30 recent MDHQ integrations are PERSONALIZED.
- Current fix path: support ticket + manual DB update of `lis_emr.ehr_integrations.report_option`. No admin UI/API post-creation.
- ACs: (1) provider portal exposes report style per EHR integration, editable by practice's own admins; (2) takes effect next push (read fresh per push); (3) audit trail who/when; (4) auto-integrate form require/carry over reportOption instead of silent CLASSIC default.
- Push pipeline mapping (from ticket): lis-backend-emr-v2 result-generation.service.ts:1131 / result-generation.processor.ts:222 (CLASSIC → add_report '1' classic PDF, PERSONALIZED → '2' modern).
- Immediate remediation for 746900 handled separately (IT DB update + re-push 17 reports) — NOT in this ticket's scope.

### Lesson injection (ENGINEERING-LESSONS, sparse k=2)
1. **Owner-scoped, not actor** — 解析 per-owner 屬性（timezone、settings）要用資源擁有者的 id，不是 JWT actor 的；admin 代操作會打破 actor lookup。→ portal mutation 的 scoping 必須綁 practice/integration 的 owner，audit 記 actor。
2. **資料違反現行設定 ≠ engine bug — 先為設定變更定年**（反向教訓部分）— 任何 user 可自行編輯、又被引擎當驗證依據的設定表，要有 updated_at 或 audit log。→ 本 ticket 的 audit trail AC 正是這條；實作要保證 who/when/old→new 可查。

- Enum `EhrReportOption {CLASSIC, PERSONALIZED}` prisma/schema.prisma:1201-1206; `ehr_integrations.report_option @default(CLASSIC)` schema.prisma:966.

## Approaches Considered

### [2026-08-26] Step 3 debate synthesis
- 正方核心：AC 原料（practice-admin gate = PRACTICE_SETTING_WRITE、central audit = buildAuditPromise）只在 transformer-v2 現成；slice 1（emr-v2 endpoint + carry-over）獨立止血；bearer 轉發可行（兩服務同 HS256 secret）。
- 反方核心命中：
  (b) **端到端 authz 漏洞**：transformer-v2 前門再嚴，emr-v2 PATCH 只有 clinic-scope check，同 practice 的任何 staff JWT 可直接 curl 繞過 → "practice-admin editable" 不成立，除非 emr-v2 端自己 gate。
  (c) **row identity**：duplicate LIVE rows + findFirst 任意贏家 → 使用者改了 UI 顯示的 row，push 可能讀 sibling → AC2 靜默失效且 audit 看起來乾淨。PENDING/REJECTED row 可否編輯未定義。
  (d) AC4 carry-over 是啟發式：換 vendor 時抄前 vendor 的值可疑（PERSONALIZED 可能 vendor-specific）；全新 practice 仍然靜默 CLASSIC，"require" 沒被 API contract 落實。
  (e) Third-party tab beta-gated（program 22）→ 功能只達 beta cohort；雙前端元件完全重複。
  (f) 更簡替代：portal JWT 本身帶 user_roles claim（transformer UnifiedAuthGuard 就是這樣讀的）→ emr-v2 可直接讀 signed claim 做 practice-admin gate，不需要 transformer hop 也不需要 RBAC gRPC。
  (g) 可測性：跨服務 contract 只能 mock；authz gap 是 system property，單 repo 測試測不到——把 gate 放在 emr-v2 資源端就變成單 repo 可測的 negative test。MySQL 物理欄位型別未驗證（migration 是 Postgres 語法），mock 測不到，要 live 驗證。
- **綜合後傾向**：把 enforcement 放在資源擁有端（emr-v2）而不是 gateway —— 呼應 Owner-scoped lesson 與可測性（negative test 變單 repo 可寫）。direct-path 版（不動 transformer-v2）成為 default 推薦；transformer-v2 中繼版列為替代（換取 central AuditLogService + canonical RBAC，代價：新 upstream client + 後門仍需 emr-v2 端處理 + 跨 4 repo）。
- Row identity 對策（in scope）：PATCH by integration id + 限定可編輯狀態（default: LIVE only）+ 偵測同 clinic(+vendor) 其他 LIVE sibling → response/log 大聲標示；dedupe + unique constraint 本體列 follow-up flag 給 reporter。
- 待 Leo/product 確認：全新 practice 無前行 row 時預設值（schema default CLASSIC vs ops 慣例 PERSONALIZED, VP-16734）。
