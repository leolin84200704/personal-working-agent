## Ticket Analysis
- P1 Story, reporter Mingxi Li, assignee me. Linked: LBS-1684 (Done, Rui Chen) = pricing side.
- Clinic/practice 128087 = Boulder Longevity Institute (prod-verified: ehr_integrations FULL_INTEGRATION LIVE, customer 11078, MDHQ vendor, SFTP/HL7 order path, ordering_enabled=1, msh06=11078; second row customer_id=-1 RESULT_ONLY).
- Portal flow applies 5% at checkout via pricing `GET /item/promotion/getCustomerPromotion?customer_id=X`; EHR flow (emr-v2 computes + charges total itself) does not → clinic overpays 5% on EHR orders.

## Ground Truth (verified 2026-08-04)
- Pricing commit 92a38f1 (origin/main, LBS-1684): clinic promo keyed on **JWT clinic_id claim** (not query param); returns `[{requireamount:0, isPercent:1, amount:0.95}]` for clinic 128087; mutually exclusive with special-customer promo (11432 Aks / 1010063 non-Aks: 0.9 if >= $600). Query param `customer_id` must match JWT customer_id claim unless internal_user_role=admin (emr-v2 payloads carry admin → bypass).
- Portal parity math (va-portal order.js totalPriceAfterClientPromo + checkout paymentMethod.js): promo applied AFTER coupon to running total INCLUDING lab processing fee/shipping/tax/concierge; per promo `if (price >= requireamount) price = isPercent===1 ? price*amount : price-amount`; toFixed(2). Payload: total = discounted; discount_amount = pre−post; v2 discounts[] = {discount_type:'client_promo', discount_amount} (no applied_item_ids).
- emr-v2 chokepoint: `parser.service.ts assembleOrderFrontend()` shared by HL7 (parse ~:400) and API intake (assembleWithNyRouting ~:808); total = actualPrice + labProcessingFee (~:693); NY $80 added post-assembly. Finalizer charges total verbatim (order-finalizer.service.ts:92). Legacy billing addOrderWrapUp trusts caller total/discount_amount (Java OrderFrontend has the field; does NOT subtract it again). v2 placeOrder mapper has dormant PlaceOrderDiscount[] slot.
- Auth: must use per-user JWT (TokenHelperService, claims carry clinic_id=ehr_integrations override=128087); static VIBRANT_API_TOKEN has no clinic_id claim → would never match promo.

## Approaches Considered
- **A (recommended): call getCustomerPromotion in assembleOrderFrontend**, portal-mirror math on (actualPrice + labFee), fail-open + loud structured log, set total/discount_amount, mapper emits discounts[] client_promo. Generic — no hardcoded clinic in emr-v2; pricing stays single source of truth.
- **B (rejected unless Leo prefers): env-config map in emr-v2** (CLINIC_PROMOS=128087:0.95) at same chokepoint. Kills HTTP/JWT/env risk but creates second source of truth; drifts when pricing table changes.

## Debate Findings (2026-08-04)
PRO: chokepoint unique & correct; per-user JWT is the only viable auth (clinic_id claim); fail-open right for money-in (blocked order worse than missed 5%); parity is line-by-line mirror; discounts[] slot pre-existed.
CON (confirmed):
1. **Staging env-crossing**: pricing verifies ONE secret per env (kuberEnv.go:26-35 — Aks→PRODUCTION_JWT_SECRET else STAGING_JWT_SECRET); getLabProcessingFee hardcodes generateToken(payload,true)+prod URL → staging emr-v2 would hit PROD pricing or 401. Mitigation: follow sendOrder's env-driven pattern (isProd = process.env.env==='prod') + URL env override.
2. **No Sentry/alerting in emr-v2 src** — fail-open needs a structured log marker (e.g. [CUSTOMER_PROMO_LOOKUP_FAILED]) so agent-layer/Sentry watch can catch it, else bug reproduces silently.
3. **Replay transitional mismatch**: already-charged (full price) stuck orders re-parsed post-deploy place at discounted total; billing tolerates charged>total silently (OrderServiceImpl.java:1603). Reverse direction (promo removed later) hard-fails if diff > $0.05.
4. **v2 placeOrder path untested** with discounts[]/reduced total_charge — 128087 is legacy HL7 path so de facto dormant; log warn if discount>0 on API path.
5. Edit-order surcharge-back risk (EditOrderServiceImpl diff-based): support edit recomputing without promo would claw back the 5%. Portal has same exposure; note only.
6. requireamount base divergence (EMR base excludes shipping/tax/merch) — immaterial for 128087 (requireamount=0), material only if 11432-style threshold promo ever EHR-orders.
