### What the code does today (lis-backend-emr-v2, origin/main ebb104f)
Two distinct intake paths — the ticket says "endpoint", which is ambiguous between them:
1. **HL7 file intake (SFTP, the vendor path the blocker ticket describes).**
   `services/parser.service.ts:174-196` is the authoritative resolve: ORC-12.1 -> if length <= 7
   `fetchById` else `fetchByNpi`; `clinic_id` comes entirely from the matched `ehr_integrations`
   row; `!clinic_id || clinic_id === 0` -> `customer_not_found`. **No practice/clinic identifier
   from the message participates in resolution.**
   `processors/hl7-order.processor.ts:364-500` `resolveIntegration(npi, MSH-4)` already implements a
   two-step provider-then-practice cascade (step 2: `clinic_id = MSH-4 AND customer_id = '-1' AND
   ordering_enabled`) — but its result is **advisory only** (logging + ordering-provider email);
   it does not place the order. Its own doc comment says step 2 "will move to practice_integrations
   once VP-16164 lands" — and VP-16164 is Inactive. As of 2026-08-21 prod there are 36
   `customer_id='-1'` clinic-level rows and **0** with `ordering_enabled=1`, so that branch has
   never fired in production.
2. **REST place-order API** (`order-intake/`, VP-17283/17472/17628). Here `customer_id`/`clinic_id`
   come from the **JWT**, not the body (`order-intake-request.dto.ts`); `orderingProviderId` is
   optional and only cross-checked against token scope. Accepting a body-level practice ID here is
   a different change with a different threat model (a caller asserting someone else's clinic).

### Why the ticket premise is already partly falsified (prod evidence, 08-20/21)
Source: STM `HL7-NPI-PRACTICE-MATCH-20260820.md`, `reference/hl7-practice-field-by-vendor-20260821.csv`,
`reference/hl7-practice-vs-sent-clinic-mismatch-20260821.csv`.
- The ticket opens "Once vendors confirm they will send a practice ID". Measured over ~180 days of
  real orders, **5 of the 6 vendors that actually send orders (MDHQ, THM, OptiMantra,
  Practice Fusion, NICHOLS) have no usable practice field at all** — ORC-12 carries the NPI and
  MSH-4 is predominantly the Vibrant **customer_id** (i.e. `msh06_value`), not a clinic_id. Only
  ~24% of orders arrive carrying any identifier we recognise as a clinic_id.
- **FOLLOWTHATPATIENT (Next Health) already sends the Vibrant clinic_id twice — MSH-6 and ORC-17 —
  and emr-v2 reads neither.** That is the only vendor with a proven, reproducible misroute:
  sample 2597376 (2026-07-16) said clinic 36290 in both fields and we booked 2930, because
  customer 43262 is attached to 4 clinics and the resolve does not look at clinic.
- Counter-evidence against naively keying on MSH-4: clinic 6212's two 2026-08 orders carry
  MSH-4=139134 (a different customer's id) and resolve successfully today; switching to
  `(npi, MSH-4)` would turn them into `customer_not_found`. Practice-attribution must be a
  **layered fallback**, never a replacement of the ORC-12 resolve.

### Lesson injection (WORK-LOOP Step 1.4, framework/ENGINEERING-LESSONS.md § 設計判斷)
- **"Owner-scoped, not actor"** — 解析 per-owner 屬性要用資源擁有者的 id，不是 JWT actor 的。
  This is exactly the defect: the clinic is being derived from the ordering provider (the actor)
  rather than from the practice that sent the order (the owner). Any design that keeps deriving
  clinic from the provider row will keep dice-rolling for multi-clinic providers.
- **"Caller 能自己修正的失敗要回 4xx，不要回 5xx"** — 合法輸入推導出空結果是拒絕不是崩潰；回可被
  對方引用的 reason/code，用對方送進來的詞彙回答，不要回內部 id. Directly governs case 2 of the
  open PM question: a practice ID that does not match the provider's clinics is a rejection with a
  quotable reason echoing the vendor's own value — not a 5xx, and not a silent reroute.

## Approaches Considered
(Not yet debated — the ticket cannot be scoped until the two external gates clear. Recorded here
so the shape is not re-derived.)

- **A. Layered fallback in the HL7 parser** (recommended shape once unblocked): keep ORC-12 ->
  customer as the primary resolve; when the message carries a practice identifier, use it to
  *disambiguate* which of the provider's clinics the order belongs to, and only fall back to the
  current single-row behaviour when absent. Preserves every order that works today.
- **B. Read MSH-6 / ORC-17 for FOLLOWTHATPATIENT now** — the only slice with zero vendor
  dependency (they already send it) and a proven misroute. Needs the vendor's written confirmation
  that the field always carries a Vibrant clinic_id, plus per-vendor gating so other vendors'
  MSH-6 (which holds customer_id) is not misread.
- **C. Data-side only** — split multi-clinic provider accounts into one account per location
  (PM/ops work, `reference/pm-handoff-followthatpatient-20260821.md`). No code, but does not
  generalise past Next Health.
- **D. Wait for VP-16164 + VP-16166** — the originally designed path (practice_integrations table +
  quarantine). Both non-active; needs PM to revive.

## Retrospective

### Result vs initial assumption
The ticket arrived as a plain Story in Dev To Do, i.e. presented as ready to build. The initial
assumption on reading the title was "add a field to the intake path". Final result: no code, and
the story's own premise needed correcting on the ticket. What made the difference was retrieval
before analysis — the 08-20/21 practice-attribution work (STM HL7-NPI-PRACTICE-MATCH-20260820 plus
the reference CSVs) already contained the measured per-vendor answer to the question this story is
waiting on vendors to answer. Reading the code alone would have produced a plausible design that
regressed live orders (keying on MSH-4 would turn clinic 6212's currently-successful orders into
customer_not_found).

### Failure analysis
No failures this session. One near-miss worth naming: the temptation to design the layered fallback
and present it as the plan. It would have been unverifiable — the acceptance behaviour is a product
decision that has not been made, so any test plan would have been asserting my own invented
semantics. WORK-LOOP's "寫不出 Test plan 的方案不能進 Step 5" caught it.

### Pattern recognition

  was two levels down. Reading the linked-issue graph AND the sibling epic children was what
  surfaced VP-16164 being Inactive — which invalidates one of the four acceptance criteria outright.
- Matches "Owner-scoped, not actor" (ENGINEERING-LESSONS § 設計判斷) exactly: clinic is derived from
  the ordering provider rather than the practice that sent the order. Same shape as the address /

### Confidence
4/5 — independent retrieval, code reading, Jira graph traversal and the comment draft. Leo was
needed only for the decision to write to Jira (a standing rule said draft-only) and for the
transition instruction.

### Factory distillation check
Two candidates, both portable once the company/system names are removed:
1. **A workflow with no direct edge to the state you need is a two-hop, not an error.** Reaching
   Dev Blocked from Dev To Do required passing through Dev In Progress. Generic form: when a state
   machine exposed by a third-party tool has no transition to the target state, enumerate the
   transitions from the intermediate states rather than concluding the target is unreachable — and
   record the hop count, because the intermediate state lands in the audit history and someone will
   ask why. Thin, but it is a real reusable fact about driving external workflow engines.
2. **A guard that refuses to run on a dirty tree turns one forgotten commit into an unbounded
   outage of the thing it guards.** This is the stronger one — see Lessons Learned below. Worth a
   lesson PR to project-agent-factory: the guard was right to stop, wrong to stop silently and
   indefinitely. Recommend proposing the enforcement shape (escalate after N consecutive aborts:
   notify loudly, or proceed read-only, or auto-commit with a marker) rather than the prose rule.

## Lessons Learned

### Technical
- The practice-attribution problem is not "vendors will send a practice ID and we need to read it".
  Measured over ~180 days: five of six active vendors send nothing usable, and the one field that
  looks like a practice id (MSH-4) usually holds the provider's Vibrant account number. Any future
  design must be a layered fallback on top of the existing ORC-12 provider resolve. Replacing the
  resolve regresses live orders — there is a named counter-example (clinic 6212's 2026-08 orders).
- `hl7-order.processor.ts:364-500` already contains a provider-then-practice cascade, but it is
  advisory (logging + provider email) and its practice branch has never fired in production
  (0 rows with `customer_id='-1'` and `ordering_enabled=1`). It is the natural seam for this work,
  but it is a seam, not an implementation.

### Process
- **Read the linked-issue graph and the epic's children before believing a ticket's status.**
  VP-17827 read as Dev To Do; the truth was one blocked blocker, one unmade product decision, and
  one Inactive data-model story that kills an acceptance criterion. None of that is visible on the
  ticket itself.
- **Answer the automation.** VP-17826's "please provide blocker details" prompt had sat unanswered
  since 08-21. A blocked ticket with no recorded blocker is indistinguishable from a forgotten one,
  and it is the assignee who pays for the ambiguity. Writing the comment in exactly the two-part
  shape the automation asks for also pre-empts it firing again on the transition.
- **When correcting a ticket's premise, lead with the measurement, not the disagreement.** The
  comment states the per-vendor counts and the one reproducible mis-routed order, then draws the
  scope conclusion. That is what makes "the fallback is the majority path" a finding rather than an
  opinion.

### Tooling
- Dream pipeline aborted three consecutive nights (08-21/22/23): "ABORT: uncommitted changes to
  tracked memory files — storage/short_term_memory/VP-17812.md". Last good run 08-20, which is
  exactly why every `_index.md` read `Last updated: 2026-08-20`. The guard only inspects TRACKED
  files, so new untracked STM files do not trip it.
  The guard's own comment says "a dirty memory file is a signal, not an obstacle" — but as written
  it is an obstacle with no escalation: one forgotten commit silently stops the entire distillation
  layer for an unbounded number of nights, and the only symptom is a stale date inside a file
  nobody re-reads. The staleness check in CLAUDE.md is what caught it, three days late.
  Down-push candidate (ENFORCEMENT-LADDER): the guard should escalate on repeat — abort once, then
  on the second consecutive abort either notify loudly or run in a read-only/no-write mode, so the
  failure cannot be silent for more than one night.
