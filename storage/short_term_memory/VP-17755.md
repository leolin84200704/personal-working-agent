## Approaches Considered

### [2026-08-27] 反方（Explore subagent）判定 REVISE：刪 gate，不要恢復 writer
- 恢復 writer 的三個獨立致命傷：
  (1) 註解塊的成功判準 `kafka[0].errorCode == 0` 是假訊號——`sendNotification`
  （azure-notification-producer.ts:306-348）失敗時 enqueue Bull 後回 **syntheticSuccess**
  （硬寫 errorCode:0）→ 會為「還在重試、可能最終失敗」的信寫 24h 抑制 key，把可恢復失敗變永久抑制；
  (2) 多 panel 陸續 finalize 時 per-sample 24h key 會靜默丟掉後續合法通知——用 17753 要修的
  同類靜默遺失去修一個幾乎不存在的重複問題；
  (3) race：check(:1096) 與 write(:1581) 相隔 ~500 行、中間 listSample 內有硬寫 5s sleep、
  3 replicas → 同 sample 併發事件幾乎必然雙雙通過，gate 給不出它宣稱的保證。
  另 cheackRedisNolock catch 無 return（Redis 抖動 → undefined → falsy → 整段 email 被跳過）——
  重新啟用它等於在送信路徑上加一個靜默丟信點。
- **採納方案**：刪 :1094-1101 gate + 刪 :1581-1587 註解 writer。淨效果：少一次 Redis round-trip、
  少一個靜默丟信危險點、code 不再暗示不存在的 dedup 保證。行為 = 維持現狀（per-event）。
- 範圍紀律：sibling 死 gate `consume_report_ready_for_patient`（:1697，同樣無 writer）**不動**，
  記錄於此供 Leo 決定要不要另開票。special_request_1（:1065）在 gate 之前送、不受影響。

## Failures

### [2026-08-27] `git add -A` 在共用 checkout 掃進了別人的編輯
- 現象：commit 61e6e70 目標只含 VP-17753 變更，實際混入了 Leo 同時在 working tree 做的
  VP-17755 gate 移除——違反 Leo 明定的「一票一斷點 commit」。
- Root cause：本 session 假設 checkout 為自己獨占，用 `git add -A` 全量 staging；實際上
  Leo 的互動 session 同時在編輯同一份 working tree（同機同 path，非 worktree 隔離）。
- 可預防：staging 一律點名檔案（`git add <paths>`）+ commit 前 `git status -s` 對照
  「這次我改了哪些檔案」清單；或共用機器上先 `git stash list`/`status` 偵測第三方編輯。
- 交接訊號：對方 session 以 cross-session message 叫停，本 session 立即停止 git 操作。
