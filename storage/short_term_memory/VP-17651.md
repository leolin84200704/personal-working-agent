## Working hypothesis (unconfirmed — needs Datadog)
Failure was systemic on the server side during an Aug 6-8 window and was cleared by the 08-08 pod replacement. Top suspect: wedged Puppeteer browser pool — `/health` returns ok WITHOUT exercising the pool (server.js:116), so a dead pool passes liveness forever while every /pdf 500s (poolAcquireTimeout 10s). Matches: every report/account/network fails, render-side (viewer) still fine, nothing reproducible after 08-08.
Ruled out for the live my-calendar flow: CORS (allowed + verified), engine auth (none), token mismatch, gateway timeout (engine max 33s < 60s), report-pdf FE code path (works today end-to-end).

## Hardening items found (regardless of root cause)
1. report-pdf-engine `/health` doesn't exercise the browser pool → wedged pool is invisible to K8s. Add pool-aware readiness (e.g. fail readiness after N consecutive acquire failures).
2. Stale viewer build at www.vibrant-america.com/portal/report still calls legacy pdf-engine-v2 → breaks silently when legacy decommissions; also if redeployed with the new bundle, that origin is MISSING from engine CORS allowlist (would 100% block downloads).
3. va-portal PatientProfilePage (NewReportService/ChipsWithAction) calls engine directly — origin now portal.vibrant-wellness.com (allowed) after the patientpage redirect; keep in mind if domain moves again.

## ROOT CAUSE CONFIRMED (Datadog, 2026-08-10 after Leo /mcp auth)
- `service:report-pdf-engine "ResourceRequest timed out"` = generic-pool acquire timeout (browser-pool exhaustion) → Fastify 500. 236 hits 2026-08-05→08-10.
- Timeline (hourly): small bursts 08-03→08-05 (1-14), **08-06 18Z = 88**, **08-07 15Z = 75 + 16Z = 54** (= 8-9:30am PT, the morning the customer recorded the Loom; ticket filed 13:37 PT), ZERO after 08-07 16:30Z. Self-recovered when the burst ended — NOT a wedged pool, pure capacity: 5 pods × 2 browsers = 10 concurrent renders, renders hold a browser 2-33s, acquire timeout only 10s.
- Peak-hour failure rate ~10% (18Z: 700×200 + 88×500; 15Z: 768×200 + 75×500). Victims mostly GET /pdf (interactive downloads, my-calendar flow: report.vibrant-wellness.com printable URLs, many distinct users/timezones) + some internal POST /pdf (base-report-service batch) competing for the same pool.
- Earlier pool-wedge/health-check hypothesis CORRECTED by evidence: pool recovers on its own; a pool-aware readiness probe would make bursts WORSE (removes pods from rotation). Do not ship that.
- Security observation (out of scope, for Leo): every download URL carries the SAME long-lived admin test JWT (test@vibrant-america.com, userId 54674, exp 2062) regardless of user — my-calendar's report links apparently run on a shared service token.
