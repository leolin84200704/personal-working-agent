## Approaches Considered

### [2026-09-01] Design v2 (post-debate; shared debate with VP-18066)

- Converter: pure mechanical pascalCodeToSnake (insert _ at [a-z0-9]->[A-Z] and
  [A-Z]->[A-Z][a-z] boundaries, lowercase; already-snake passthrough,
  idempotent). Applied at enrichment return point (order-intake-enrichment
  .service.ts:353) so BOTH the wire response and the persisted error column
  (order-intake.service.ts:227-233 joins failure codes) agree. Historical rows
  keep PascalCase in error column — mixed data, note for reconciliation.
- STEP 0 before freezing fixture: pin the REAL eligibility-check code enum
  (only PFSAMaleOnly observed in-repo, rest are from mintlify docs) via
  Confluence "Order Eligibility Check API" + staging probes.
- Fixture: one JSON vendored byte-identical into emr-v2 and pricing (Rui);
  contract test in each repo runs its converter over fixture inputs and
  asserts exact outputs. This replaces the unenforceable "table in a comment".
- rejected + failures[]: additive; reason/errorCodes untouched; errorCodes
  NEVER converted; human reason from enrichment where entity ids exist
  (patient X not found), per-reason template fallback for the 3 service-level
  rejection sites (order-intake.service.ts:121/164/293); paymentFailReason is
  internal — template, never verbatim.
- Sequencing: this PR lands before VP-18066's emr-v2 PR (both touch
  order-intake.controller.spec.ts).
