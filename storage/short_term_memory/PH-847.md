# PH-847 — Portal API: one reason taxonomy across quote and order

## Ticket Analysis

### [2026-08-31] Intake

- PH-847 (Product Hub), Task, To Do, UNASSIGNED, P2, reporter Nan Wu,
  created 2026-08-12. No VP implementation twin exists yet (JQL text search:
  only PH-847 itself). Contract: https://apidemo.mintlify.app/concepts/orders
- Ticket: same condition gets different reason codes on quote vs order —
  PatientNotFound (quote) vs patient_not_found (order). To close: one taxonomy,
  same machine code + casing for the same business fact.

### Current-state map (verified in code 2026-08-31)

- **Quote** = `POST /item/catalog/quote` in LIS-backend-v2-pricing (Go),
  handler/item_catalog.go createQuote (~L1441). Gateway exposes as /v1/quote.
  Flow: ResolveExternalCodes → BuildEligibilityLineItems → order-management
  `POST {ORDER_BASE_URL}/orders/eligibility-check` (source=API, pricing's own
  service JWT) → ineligible ⇒ 200 `{eligible:false, failures}` with
  **failures[].code passed through VERBATIM** (PascalCase: PatientNotFound,
  CustomerNotFound, PatientNotInClinic, IncompletePatientInfo,
  GeneticTestAlreadyOrdered, PFSAMaleOnly, ProzFollowupNoPreviousOrder,
  SkincareFollowupNoPreviousOrder — list from mintlify concepts/orders).
  Unknown test codes ⇒ 400 `{"error": prose, "unknown_codes":[...]}` (docs say
  `unknownCodes` — docs/code key mismatch, snake in code). Other 400s are prose
  `{"error": "..."}` with NO machine code at all (no envelope/requestId —
  VP-17691 envelope was scoped to emr-v2's two controllers only).
- **Order** = `POST /orders` → emr-v2 order-intake. Two failure layers:
  1. emr-v2's own enrichment fast-fail (BEFORE eligibility):
     kind:'rejected', snake_case reasons — patient_not_found
     (order-intake-enrichment.service.ts:188), provider_scope_mismatch (:177,
     :143), default_provider_unresolved (:143), unrecognized_test_codes (:268),
     no_orderable_items (:334), default_provider_not_configured
     (order-intake.service.ts:122), plus INVALID_* / MISSING_* envelope codes.
  2. eligibility-check layer: kind:'ineligible', failures passed through
     VERBATIM (DTO comment order-intake-request.dto.ts:54 "surfaced verbatim
     from the eligibility-check API") — SAME PascalCase codes as quote.
- **The ticket's example decoded**: missing patient on quote reaches the
  eligibility check (pricing never resolves the patient itself) ⇒
  PatientNotFound; on order, emr-v2 resolves the patient in enrichment and
  fast-fails ⇒ patient_not_found. Same fact, different layer, different code.
  Second same-fact divergence: unknown test codes — quote 400
  unknown_codes/prose vs order rejected `unrecognized_test_codes`.
- Producer of PascalCase codes = **order-management** (order team), consumed by
  many sources (Source enum NewOrder|Shopify|...|API) — changing it there has
  cross-team, cross-channel blast radius.
- mintlify concepts/orders ALREADY announces "reason codes are being unified
  across the two endpoints" and tells clients to treat the list as
  non-exhaustive + fall back to human-readable reason. Partners are beta-scale
  (GetHealthy sandbox; Prospera upcoming per VP-17812).

### Injected lessons (ENGINEERING-LESSONS, sparse k=1)

- **Sync sibling encodings of an invariant** — 同一個語意的衍生點要用 single
  source 一起改，別讓兩份表各自漂移。(→ taxonomy normalization will live in TWO
  services (Go pricing + TS emr-v2); prefer a MECHANICAL Pascal→snake converter
  over a hand-maintained mapping table so there is nothing to keep in sync;
  contract-test the 8 known codes identically on both sides.)

## Approaches Considered

### [2026-08-31] Sketch (pre-debate, pending Leo direction)

- **Recommended: snake_case canonical, normalize at the two partner-facing
  edges.** Mechanical PascalCase→snake_case conversion (acronym-aware:
  PFSAMaleOnly→pfsa_male_only) applied to eligibility failures[].code in BOTH
  pricing createQuote and emr-v2 intake ineligible path; keep human reason
  verbatim; unknown future codes convert consistently without table updates.
  Quote's unknown-code 400 gains machine code `unrecognized_test_codes`.
  No order-management change (edge mapping keeps blast radius inside the API
  product). Rationale for snake: order contract (statuses, rejection reasons,
  cancellation reasons) is already snake_case and shipped/documented; docs
  already announce unification.
- Alt B: change order-management producer — one place but cross-team + all
  channels inherit; rejected unless order team wants it.
- Alt C: emr-v2 adopts PascalCase — breaks shipped documented order contract;
  rejected.
- Open: quote-side contract change is breaking for quote consumers parsing
  PascalCase today (beta partners only); needs PM (Nan) sign-off + mintlify
  update + partner comms. Repos span pricing (Go) + emr-v2 (TS) — likely one
  VP ticket, two PRs.

### [2026-08-31] Direction agreed with Leo (Step 4)

- Leo asked for the current quote/order diff, then for my judgment on the
  customer-friction-free unification, then OK'd drafting the Nan comment.
- Agreed model: snake_case canonical; mechanical acronym-aware Pascal→snake
  normalization at both edges; `failures[{code,reason}]` becomes the uniform
  business-failure carrier on BOTH endpoints (additive on order rejected —
  reason/errorCodes kept); quote unknown-testCodes moves from prose 400 into
  outcome (eligible:false + unrecognized_test_codes + errorCodes); HTTP
  semantics unchanged (quote 200 eligible:false vs order 422 — documented,
  not unified); quote request-error envelope port = optional scope extension,
  Nan's call. Rollout: docs first → partner notice → sandbox → soak → prod;
  NO dual-emit (beta scale, not worth the debt).
- Order-side changes confirmed with Leo as "small but required": (1) ineligible
  failures[].code normalization (order itself mixes casing today — rejected
  snake vs ineligible Pascal), (2) additive failures[] on rejected. Everything
  else on order is the canon and stays.
- Comment for Nan drafted at drafts/PH-847-nan-comment-draft.md; Leo reviewed
  the full text inline, asked one edit (last paragraph: ask PM to open the
  implementation tickets, not us), then said 發布 — POSTED to PH-847 as
