# VP-17591 - Work Loop Record

## Ticket Analysis

Bug, P2, `jira_escalated`. Reporter Mingxi Li, assignee Leo. Order 2607316527,
patient JONATHAN HAFT (patient_id 3160709), customer 35353 / clinic 128087.
Symptom: EMR order file contains the patient address, but the payload sent to
Order service has every address field blank.

Leo asked to look at this together with VP-17544 — correctly, they are the same
family: upstream's patient-completeness check is **DOB + gender + address**, and
VP-17544 covered the first two while address was silently broken.

### Evidence chain (all three verified)

| | |
|---|---|
| HL7 file | `PID\|1\|11078.1914\|\|\|HAFT^JONATHAN^\|\|19771007\|M\|\|\|89 Vagneur Lane^^Basalt^CO^81621\|\|970-948-3168\|...` — address complete |
| Patient record (`GetPatient` 3160709) | `{"address_type":"shipping","street_address":"89 Vagneur Ln","city":"Basalt","state":"CO","zipcode":"81621-9100","address_confirmed":true,"is_primary_address":false}` |
| Sent to order service | `{"zipcode":"","country":"238","city":"","street":"","state":""}` |

`country:"238"` is the only populated field because it is hardcoded
(`patient_country_id = 238`) — a tell that the address came from neither source.

Reading the file needed appserver04 (`/mnt/storage/EMR_storage/...`, password auth
via expect + ControlMaster); the AKS pod's PV holds only the single folder that
pod owns.

### Root cause — three independent decisions stacking

1. **`findOrCreatePatient` existing-patient branch discarded the file's address
   unconditionally** (`patientDetails = grpcPatient` replaced the whole object).
   It never even checked whether the record had an address, so "DB empty + file
   populated" was equally broken.
2. **`populateFromExisting` selected the record address with
   `if (addr.is_primary_address)`.** Reads as "pick the main one out of several"
   — correct with several, but when the only row is not flagged primary the same
   line stops being a *selection* and becomes an *exclusion*.
   **741,520 of 1,045,219 patients with an address (71%) have no primary row**, so
   the majority case sits on a branch written for the minority.
3. **order-management asks the same question differently**:
   `CorePatientService.CheckIfPatientHasAddress` keys on
   `address_type == "shipping"` and ignores `is_primary_address` → it considers
   these patients complete and never flags the empty address we send. Two
   definitions of "has an address", no error on either side.

**Root enabler for (2)**: `address_type` was **absent from the
`PatientWithDetails` address type** although `GetPatient` always returned it —
so selecting by type would not compile, leaving `is_primary_address` as the only
selectable field.

**Confirmed the data does reach us** —病灶 100% 在 emr-v2，上游不需要改。

## Decisions Made

Leo: **file wins; if absent use DB** — then narrowed for NY:
> 有 Gut Zoomer（或任何需要判別 NY 的測試）一律只能以 HL7 為標準，沒有就連 DB 都不看直接拒單。
> 多收錢的問題一定要 customer 提供完整訊息，否則因搬家等原因會有財務問題，不能到我們這裡。

So two uses, two fields:
| field | source | used for |
|---|---|---|
| `patient_state` | file, else record | shipping the kit |
| `inbound_patient_state` | **file only** | NY routing + $80 fee |

`inbound_patient_state` set unconditionally (including undefined) so "the order
did not tell us" reaches `decideGzNy` as empty → existing
`NY_ADDRESS_REQUIRED` reject path fires.

**Scope discipline**: only `parse()` (HL7) switched. `assembleWithNyRouting`
serves the **API** intake path where the caller sends only `patient_id` and never
an address — inbound-only there would reject every GZ order; that path is guarded
by eligibility-check, which validates address itself. Verified the two paths share
no call site.

**A failure that earned its keep**: my first test version hand-counted PID fields

## Failures

## Lessons Learned

- **A conditional that selects among many becomes a filter when there is one.**
  `if (isPrimary)` was written for "choose among several addresses"; with a single
  non-primary row it silently produced *no* address. When a predicate picks a
  winner, ask what it does when there is exactly one candidate that fails it.
- **Two services keying on different fields for the same concept = silent data
  loss.** Neither side errors: the strict one produces empty, the lenient one sees
  "complete" and does not complain.
- **A missing optional field in a type can steer behaviour.** `address_type`
  absent from the interface made the correct selector uncompilable, so the wrong
  one was the only option available.
- **Stale data is not a smaller version of missing data — for money decisions it
  is worse.** Leo's rule: never infer a billable attribute from stored state the
  current request did not assert. Missing → reject and make the sender supply it.
