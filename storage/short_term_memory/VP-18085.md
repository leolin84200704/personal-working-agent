### Code path (lis-backend-emr-v2 main @ 03637bc, synced 2026-09-09)
- `order-intake-enrichment.service.ts` step 4 (L195-275): `productMapClient.resolve(req.testCodes)`
  -> one line item per code, in order -> switch on item_type joins mapping cache.
  `TESTGROUP` items are deduped by test id (`seenTestIds`, L236-246); `packagePriceId`
  (GROUP) and `bundleId` items are NOT deduped at all -> two groups both go to assembly.
- `product-map-client.service.ts resolve()` preserves repeats (`codes.map(resolved.get)`),
  so an exact repeated code yields two identical line items.
- Rejection plumbing already exists: `{ok:false, kind:'rejected', reason, errorCodes}` ->
  `order-intake.service.ts` L239-253 writes order_intake.status=rejected + returns
  `failures: rejectionFailures(reason, {errorCodes})` -> controller L182 sets 422.
  `order-intake-failures.ts` REJECTION_MESSAGES needs a new entry for the new reason.
- Existing spec `order-intake-enrichment.service.spec.ts` L222 "happy path ... dedups"
  asserts `['GUT_ZOOMER','GUT_ZOOMER','SOME_BUNDLE']` is silently deduped and placed —
  the new rule flips that expectation (contract says reject).

## Approaches Considered

### [2026-09-09 10:40]
- **A (recommended, emr-v2 only)**: in enrichment right after productMap resolve succeeds,
  two-layer duplicate detection over the sent codes:
  1. resolved `item_type:item_id` seen twice -> duplicate (exact repeat, deprecated alias);
  2. canonical key = trim().toUpperCase() with ONE trailing `_DBS` stripped, seen twice ->
     duplicate (collection-variant twin).
  Reject `duplicate_test_codes` (422 via existing rejected path), errorCodes = offending
  codes as sent, REJECTION_MESSAGES: "the same test appears more than once: X, Y".
  Log at warn with both codes. Precedence: after unrecognized/unsupported (unknown codes
  are the more fundamental error), before mapping-cache join.
- **B (authoritative, cross-repo)**: pricing adds a `product_family` / `dbs_of` field to
  productMap line items from `dbs_mapping` (or a new endpoint); emr-v2 keys on it.
  Blocked on pricing team + dbs_mapping population is unverified on staging (API empty).
  Proposed as follow-up so the suffix heuristic can be retired.
- **C (rejected)**: use `displayName` equality from the legacy mapping cache — a display
  string, collision-prone, and not part of any contract.
- **D (rejected)**: put the rule in pricing `ResolveExternalCodes` so quote and order share
  it — quote parity is desirable (PH-847 taxonomy) but the ticket is scoped to POST /orders
  and pricing is another team's repo; raise as a question, not a silent scope change.

### [2026-09-09 10:55] Debate synthesis (2 subagents, PRO/CON)
- PRO: insertion point L210-230 already has `sentCodes`/`idToCode` for caller-vocabulary
  naming (VP-17686 precedent); rejection path is existing tested plumbing; layer 1 is free
  correctness (exact repeat / deprecated alias currently silently deduped = latent contract
  violation); layer 2 is the only signal available today since item ids are provably disjoint;
  emr-v2 is the contract enforcement boundary (VP-18080 taxonomy lives here); swappable for a
  dbs_mapping lookup later without changing response shape.
- CON (accepted points -> folded into plan): (1) all unit tests are mock-input — behaviour-level
  proof must be a staging round-trip with the real productMap after deploy, plus a vendored
  catalog-codes fixture asserting the `_DBS` convention so the assumption is pinned and visible;
  (2) case-fold the canonical key (layer 1 is case-independent anyway); (3) precedence must be
  explicit and tested: unrecognized/unsupported first, then duplicate, then mapping-cache join;
  (4) placerId retry is unaffected — a resend hits the order_intake duplicate short-circuit
  before enrichment, and a `rejected` row is reclaimable so the partner can fix and resend.
- CON (out of reach, declared as limits): bundle-member overlap (FOOD_BUNDLE containing a
  zoomer + that zoomer's DBS twin) — cached `Bundle` carries no member list and twin-through-
  bundle needs dbs_mapping; a future `_DBS` code that is not a suffix — mitigated by the warn
  log, not detectable. Deprecated code + active replacement in one order IS rejected by
  layer 1 — consistent with "one version per order".
- Net: A stands, with the fixture test, case-fold, explicit precedence, and a follow-up
  proposal for pricing to expose dbs_mapping (approach B) recorded as the retirement path.
