# VP-17538 — customerPay must try payment methods one by one

## Origin
Leo 2026-07-29: "按定义的新 wallet payment priority 逻辑，应该一个个尝试" — asked to file the ticket
and change the code directly. Follows the same session's customerPay failure diagnosis.

## Root problem
`finalize()` charged only `getFirstPaymentMethod()` = `customer_payment_methods[0]` (clinic array
reachable only when customer array empty; Java ChargeClient parity). No fallback -> one dead method
at index 0 makes an entire account unpayable. Staging customer 3194: 3x stripe ACH rows ahead of a
working stax visa (id 366147) -> order_intake 125/127/136 all rejected payment_failed.

## Change (PR #305 draft -> staging, branch bugfix/leo/VP-17538)
- `ChargeClientService.getPaymentMethodCandidates()` returns the full list (customer then clinic,
  charging's own array order); `getFirstPaymentMethod()` kept as head accessor, now delegates.
- `finalize()` loops candidates, stops at first 2xx WITH payment_transaction_id (VP-17411 rule).
- Advances ONLY on a provably-no-money failure. `isIndeterminateChargeError()` (timeout/abort/
  ECONNRESET/socket hang up) halts the chain -> never double-charge on an unknown outcome.
- Exhausted list keeps the old contract (API blocks payment_failed / HL7 records + ships); the fail
  reason now enumerates every attempt. `'no payment method'` string preserved for the empty case.
- Tests: +6 finalizer cases + isIndeterminateChargeError unit; existing specs derive a 1-element
  candidate list from the old mock so prior contracts still assert. 22 suites / 234 tests pass,
  tsc clean, pre-push nest build OK.

## OPEN — the priority ORDER is not confirmed
Could not find the "new wallet payment priority" definition. Searched Jira (30 wallet/priority
tickets) and Confluence: RES V2 "Improvements for Setting, Order, Statement" defines *revenue credit*
Practice-vs-Provider wallet precedence, NOT payment-method attempt order; no repo code implements a
priority. Implemented ordering = charging API array order, NO reordering by type (refused to guess
"card before ACH" on a payment path). Isolated in `getPaymentMethodCandidates` = one-place swap.
**Asked Leo for the doc/Slack link. Do not treat the PR as final until answered.**

## Blast radius flagged to Leo
`finalize` is shared: this changes BOTH the API intake path and the legacy HL7 customerPay path.
HL7 orders that today land unpaid on a dead first method would now succeed on a later one — real
prod behavior change, wants explicit sign-off.
