## Approaches Considered

### [2026-08-31] Design v1 (pre-debate)

No existing RPC covers the full contract (patient filter + datetime window +
pagination + orderedAt). Composition design, all within emr-v2:

- Controller: extend OrderStatusController GET branch. Params present in
  LIST_MODE_PARAMS and none of orderId/placerId → list mode; no params at all →
  list mode defaults (clinic-wide, page 1). Mixing → 400
  AMBIGUOUS_ORDER_IDENTIFIER (contract). Keep customerId/clinicId REJECTED
  (guard-bypass hazard). Validation: patientId int; from/to ISO-8601 (bare
  date → 00:00:00Z), from>=to → INVALID_DATE_RANGE; page>=1; perPage 1..100,
  >100 CLAMPS (GET /patients parity); sortBy ∈ {orderedAt}; sortOrder ∈
  {asc,desc}; type errors → INVALID_FIELD_TYPE.
- Path A (patientId given): (1) ownership check via NEW v2 wrapper
  GetCustomerClinicIdByPatientId → mismatch with token customer → 404;
  (2) NEW v1 wrapper v5_SearchSamples(patient_id_list=[p],
  client_info_list.client_id_list=[tokenCustomer]) → full in-scope set
  (bounded: one patient's orders; cap guard) → in-process half-open window on
  order_time + exact sort by order_time + paginate + count.
- Path B (no patientId): GetCustomerSamplesByTimeRange(cust, from ?? 1900-01-02,
  (to ?? 2100-01-01) − 1ms) → all sample_ids asc + count; sortOrder desc →
  reverse; slice page → v5_SearchSamples(sample_id_list=pageIds) batch enrich
  (single query). GLOBAL ORDER = sample_id (≈ chronological; documented
  approximation — stable unique-key pagination, no dup/miss during iteration).
- Both: enrich placerId/orderId/testCodes from order_intake
  (customer_id = token AND sample_id IN pageIds; request_json.testCodes
  verbatim for API rows); Portal rows → orderId/placerId/testCodes null
  (mintlify already allows testCodes null for portal rows).
- Row status: NOT cheaply derivable (v5 lacks order_canceled; report status
  needs per-row RPC) → RECOMMEND asking PM to drop `status` from list rows
  (ticket prose "thin rows" supports this; status available via lookup mode).
  Fallback option (b): degraded status from kit_status+received_time only —
  collapses analyzing/report_available; needs spec note either way.
- Errors: upstream failure in list path → 503 UPSTREAM_UNAVAILABLE (no
  sensible degrade for a list); v5 missing row for an id → minimal row + warn.
- No emr-v2 schema change (order_intake tiny, existing customer_id-prefix
  indexes suffice for enrichment).

### [2026-08-31] Debate outcome (design v2 — critic verdict: redesign internals, accepted)

Critic objections ACCEPTED (evidence verified by critic in coreSamples/v2 Go):
1. **Drop GetCustomerClinicIdByPatientId ownership check** (was BLOCKER):
   v2 impl walks patient_clinics edges only → false 404 for legacy patients
   with no patient_clinics rows (Portal shows them, patient.service.ts:2922)
   and for clinic_id=null orders; empty result Redis-cached 5 min → place→poll
   loop 404s right after placement; 404 signalled IN-BAND ({code:404} in a
   200 response, patient_service.go:5449); AND grpcConfigV2 has NO staging
   defaults — every v2 service hardcodes prod 10.224.0.199:32100
   (grpc.config.ts:272-311) → staging E2E would consult prod. Ownership now
   derived from data: patient variant throws "Patient not found" (→404);
   patient exists but zero in-scope rows across full history → 404.
2. **Drop v5_SearchSamples entirely** (was BLOCKER premise): v5 runs the query
   TWICE (unpaged count), silently drops samples with null patient relation
   (v5_fillSamplesWithClinicPhlebInfo `continue`, sample.service.ts:1997) →
   count/rows skew; unguarded sort_info deref (:564) → opaque 500 for a
   naive wrapper. REPLACED by `ListSamples(id_list)` batch — the SAME RPC
   the lookup path already uses live in prod, one Prisma query upstream
   (sample.service.ts:2533), and its proto order block carries
   order_create_time, order_status, order_kit_status, order_report_status,
   order_cancel_time, isActive, order_flags, clinic_id, patient_id
   (sample.proto:781-857). emr-v2's v1 wrapper reads only sample[0] — extend
   to a batch variant (same RPC = liveness proven).
3. **"status impossible" premise FALSE** → coarse status IS derivable from the
   ListSamples order block (cancelled / sample_received / kit tier /
   report_available / placed), not bit-identical to VP-17760 derivation
   (no shipping tracking / report issue detail). Critic's killer argument for
   keeping status: Portal-placed rows have null orderId/placerId → they can
   NEVER use lookup mode → dropping status = Portal channel has no status
   anywhere in the partner API. Present PM: coarse-status (recommended) vs
   drop-status.
4. TZ handling (MAJOR): order_time crosses wire as String(Date) (server-TZ
   locale string, proto declares string); from/to parsed by new Date() in the
   CORE pod's TZ (sample.service.ts:6013) — offsetless inputs must be rejected
   or normalized to explicit UTC in emr-v2; E2E MUST include a boundary probe
   (place order at known instant, verify window membership). order_create_time
   column is DATETIME(3) (no @db.DateTime(0)) so −1ms exclusivity trick is
   sound, but stored TZ must be verified empirically.
5. Scope divergences from Portal visibility (MAJOR → PM confirm): customer-
   scope-only vs Portal clinic rule (multi-provider clinics under-covered);
   sample.customer_id (time-range filter) vs order_info.customer_id (Portal);
   isActive=false / flag-hidden orders visible in our list. → PM decision.
6. Path B latency (MAJOR): full-history id fetch repeats per page; MUST
   measure largest staging clinic BEFORE declaring viable; if marginal →
   escalate to purpose-built core RPC rather than caching.
7. Pagination drift honesty (MAJOR): desc + offset = page shift when new
   orders arrive mid-walk; asc + from-window is the safe sync idiom →
   document in mintlify.
8. Minors accepted: no-params flips 400→full-list (contract-mandated, flag as
   breaking); pre-placement intake rows (processing/rejected/failed/dry_run)
   absent from list — document "list = placed orders" or merge (PM note);
   add order_intake @@index([customer_id, sample_id]) in this PR; dedupe
   multi intake rows per sample_id (newest id wins); pre-validate end<=start
   (our 400) and map upstream "Customer not found" → empty + warn, not 503;
   echo clamped perPage.
9. Testability (accepted plan): pure module order-list.derivation.ts (mode
   discrimination, validation matrix, window filter, sort, page-slice, count,
   row mapping, request_json extraction, timestamp normalize) — table-driven
   specs, no mocks; service orchestration with mocked wrappers (seams = the
   wrappers); gRPC wrappers mock-worthless → E2E checklist mandatory
   (both-channel clinic page, pagination walk static set, tz boundary probe,
   legacy patient no-patient_clinics probe, largest-clinic latency, gateway
   GET query-string on external path).

Final composition (design v2): ids via getCustomerSamplesByTimeRange /
getPatientSamplesByTimeRange (both v1, wrapped, prod-live) → page-slice
(patientId path: full-set enrich, exact orderedAt sort, cap ~1000 + warn) →
ListSamples batch enrich (extend v1 wrapper to id_list) → local order_intake
join (placerId/orderId/testCodes). Zero new upstream dependencies, zero v2,
zero v5.
