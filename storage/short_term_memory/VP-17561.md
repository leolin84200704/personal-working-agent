# VP-17561 — on-prem Kafka -> cloud Event Hub cutover (emr-v2 result events)

## Decision
Leo 2026-07-30: "直接切, 兩個應該是一樣的, 未來直接用 cloud kafka". Assigned to Leo; he merges.
Supersedes the VP-16784/85/86/87 "don't migrate Kafka" conclusion for THIS consumer only.

## Mechanism — the merge is the switch
No manual toggle. VP-17559 (PR #311) attaches `serviceAccountName: identity-provider` +
`azure.workload.identity/use` to the prod deployment; the rolling restart lets KeyVaultService
resolve the SAS string, so `buildCloudKafkaConfig()` stops returning null and the cloud branch wins.
- before: on-prem 192.168.60.9/10/11:9095, topic `lis-general-events`
- after: general-events.servicebus.windows.net:9093, topic `general-sample-events`
- consumer group unchanged (`emr-result-consumer-cloud-production` — it was already named "cloud")
- PROD intake pod only; staging has ENABLE_KAFKA_CONSUMER=false; pusher pods skip by pod role

## Verify after deploy
`✅ Kafka consumer running on cloud cluster, topic=general-sample-events` (and NO
`Cloud Kafka config incomplete` warning), then confirm a report-finished event still enqueues a
result-generation job.

## Rollback
`KAFKA_CLOUD_ENABLED=false` in lis-emr-v2-config-prod + restart the intake pod. No deploy, no schema.

## Caveats carried into the decision
1. Offsets do not carry across clusters and subscribe uses fromBeginning:false -> the few seconds
   between on-prem stop and cloud join are never consumed (dual-publish = nothing lost upstream, but
   those messages are skipped). Spot-check result generation right after the restart.
2. staging ConfigMap has KAFKA_CLOUD_TOPIC=general-sample-events but staging's hub is
   `general-sample-events-staging` — harmless while the consumer is off, must fix before enabling.
3. Dual-publish equivalence is asserted from the 2026-05-28 verification, NOT re-measured today.
   Leo made that call explicitly.

**Consequence the rollback plan missed — duplicate result delivery.**
Caveat 1 above only anticipated the FORWARD gap (messages skipped between clusters). The REVERSE
direction overlaps instead of gapping: consumer group `emr-result-consumer-cloud-production` still
holds its **00:24Z on-prem committed offset**, so rejoining the on-prem cluster replays the entire
71-minute window the cloud consumer already processed (dual-publish = the same events exist on both).
- 01:35–01:39, first ~4 min of replay: **17 transmission records (16 samples) re-transmitted**, all
  `MDHQ` clinics, out of **35 pushes / 34 samples / 20 clients** in the cloud window.
- **The re-push is invisible as a row count.** `ensureResultTransmissionRecord` (result-generation.
  service.ts:1240) does `findFirst` on (sample_id, integration_request_id, push_scope_key) and if the
  record is < 24h old it REUSES it — resets `generation_status`/`encoding_status` and continues through
  generate → save file → SFTP transmit. Detection is `updated_at > created_at` plus the log line
  `♻️ Reusing existing transmission record`, NOT a duplicate row.
- There is no "already sent" gate to stop it: `emr_sample.result_sent` gating was **removed in
  VP-17408** (see `result-generation.service.spec.ts:271`).

**Rule this establishes:** for a consumer cut between two clusters that are dual-published, the
rollback is NOT symmetric with the cutover. Rolling back re-delivers everything processed in the
window, because the old cluster's committed offset is frozen at the moment of cutover. A cutover plan
needs an offset-forwarding (or replay-suppression) step in the ROLLBACK direction, or an idempotency
gate on the delivery side — one or the other, before the switch is thrown.

## Closed out 2026-07-31 (Jira Done)
Cutover live and verified: `✅ Kafka consumer running on cloud cluster, topic=general-sample-events`,
group joined with partition [0], consuming (lag ~0), new result records flowing.

**Incident inside this ticket — my error, not the system's.** At 01:25Z (61 min post-cutover) I saw 0
new result_transmission_records and rolled back. That was WRONG: upstream had simply produced no
report_finished events between 00:24 and 01:29; they arrived at 01:29-01:31 and the cloud pod handled
them correctly (35 records, all TRANSMITTED, one stamped with the cloud pod's own name). Costs of the
unnecessary rollback: on-prem group replay from the cutover offset re-delivered ORUs for ~17 samples
(no idempotency gate), and the two pod restarts orphaned 5 in-flight generations.
Remediation, all verified: cloud re-enabled after advancing the cloud group offset past 8,501 queued
messages (so no second duplicate wave); the 5 orphans repushed via the whitelisted
`GenerateResultHl7` gRPC and each confirmed TRANSMITTED with its HL7 on MDHQ SFTP; their stale rows
closed to GENERATION_ERROR/TRANSMISSION_ERROR with an explanatory error_message (bounded UPDATE,
5/5 verified, reverse-audited); staging ConfigMap topic corrected to general-sample-events-staging.
Lesson written to [[feedback-never-conclude-breakage-from-a-quiet-window]].
