## Why two PRs — main and stage_test have divergent copies of VP-16549

`#159` was first opened against `stage_test` and came back CONFLICTING. The cause
is not this change: **VP-16549 was landed twice, as different commits**, once on
each branch —

- `stage_test`: `11bacd3` + `42882c7` (merged by PR #157)
- `main`: `91acf9a` + `7204ad3` (merged by PR #158)

Same content, different SHAs, and the two copies place the
`import { createOAuth2Metadata, getServiceToken } from '../oauth2';` line at
slightly different offsets. A branch cut from `main` therefore cannot merge into
`stage_test`: git cannot place a *new* import line relative to two unrelated
copies of the neighbouring one. The whole conflict was that one import; every
substantive hunk auto-merged.

`main` is additionally ahead of `stage_test` by `6d4657c` "Improve Datadog
logging signal quality" (adds `logger.spec.ts` + `kafka.logger.spec.ts`), which
is why the two branches report different jest suite counts.

Resolution: `git cherry-pick 1ac7d06` onto `origin/stage_test` (applies clean —
cherry-pick rebases against the commit's own parent, so it never sees the import
ambiguity a merge does) → `feature/leo/VP-17870-stage` → PR #160. `#159` was
retargeted to `main`, where its head merges cleanly. Do not merge `#159` into
`stage_test` or vice versa.

**Repo lesson**: in `LIS-setting-consumer`, `main` and `stage_test` are not a
promote-forward pair. Cut the staging branch from `origin/stage_test` and the
main branch from `origin/main`, cherry-picking between them (this is what PRs
#157/#158 and #153/#154 already did). Branching once off `main` and aiming at
`stage_test` will conflict.

## How to verify this end-to-end (the audit-log trick)

`createKafkaProducerConfig()` calls `saveToAudit()` on every successful send,
which gRPCs into `lis-auditlog-deployment`. That service **logs the literal
INSERT** into `audit_log_production.general_audit_log`, with
`entity_snapshot` = the Postmark tag and `service_name` = 'Setting Consumer'.
So every email this service sends leaves a Datadog log line — no Postmark API
token needed.

Datadog query (log search syntax):
`service:lis-auditlog-deployment "Send pns email" billing_delta_credit_pending`

Control that the *events* are still flowing (so "no email" is not "no traffic"):
`service:lis-shipping-deployment "billing_delta_credit_pending"` — lis-shipping
is an unrelated consumer of the same general-events stream and logs
`Received Azure event:` with the full payload.
