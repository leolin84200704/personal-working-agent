## Approaches Considered
- **Read gate location.** (A, chosen) GraphQL field resolver on `EventResolver` — `Event.internal_notes` has no `@Field`; the field exists only via `@ResolveField` that returns null unless `request.userType === 'clinic'`. One choke point for every query returning `Event` (getEvents / getEventByEventId / getCancelledEvents are patient-reachable). (B) flag on `mapEventToGraphQL(event, viewer)` — 14 call sites, one forgotten flag leaks. (C) separate patient DTO — no precedent in repo, big diff.
- **Recurring exception column.** Without `updated_internal_notes`, a THIS_EVENT edit carrying internal_notes would be a silent no-op (lesson: update contract vs handler consumption). Added the column to mirror `notes`/`updated_notes` exactly (PRD FR-006 "same conventions as other appointment fields"). Cost: 1 column + 5 lines.
- **Char limit.** 2000 via class-validator `@MaxLength` at API layer, DB stays TEXT → PM can change the number without a migration.
- **AC "editing only this field sends no reschedule email".** Depends on PH-822 (TPM Review, no branch/PR in transv2 as of 2026-09-02). PRD non-goal 5 / out-of-scope 1 explicitly hands it to PH-822. Not implemented; flagged. A stop-gap (skip side-effects when the update diff is internal_notes-only) is cheap if Leo/PM want it.

## Decisions Made
- Internal user = any non-patient token (Leo 2026-09-02). Implemented as `canReadInternalNotes(userType) === (userType === 'clinic')`, fail-closed on undefined.
- Two columns: `v2_event.internal_notes`, `v2_event_exception.updated_internal_notes` (both nullable TEXT). Migration `prisma/manual-migrations/20260902_add_v2_event_internal_notes.sql` + `scripts/vp-18048-apply-migration.js` (per-schema, idempotent, verifies both columns after).
- Write gate `assertCanWriteInternalNotes(user, input)` at all 4 mutation entry points (createEvent, updateEvent, createEventByPatient, updateEventByPatient) + rescheduleClinicalConsult (which had NO patient check at all — pre-existing gap, noted).
- Kafka `addon_column` spreads the whole row in two services → both go through `omitInternalEventFields()` from one module so they cannot drift.
- Not touched: daily-report xlsx (internal recipients, PRD didn't ask), inbound Google/Outlook sync (writes `notes` from external description; never writes internal_notes), meeting-request → event creation (no source for internal notes).
- Worked in a worktree `~/src/LIS-transformer-v2.worktrees/VP-18048` (node_modules + .env symlinked to main checkout, existing convention). Local commits only, NOT pushed — Leo reviews first (lis-prod-change-gate final step).

## Retrospective
## Lessons Learned
- **Field-level GraphQL gate beats per-query stripping**: when an ObjectType is returned by N queries with mixed audiences, declare the sensitive field only via `@ResolveField` on the type's resolver and gate on request context. Prove it with a schema-building spec — a resolver-only field is exactly the "compiles but isn't there" shape.
- **Grep for `...row` spreads before adding a column**: in this repo GraphQL/emails/sync were all explicit, but both Kafka payload builders spread the whole Prisma row. A new column leaks there by default.
