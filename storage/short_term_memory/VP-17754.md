# VP-17754 - Work Loop Record

## Ticket Analysis

### [2026-08-27] 背景與關鍵翻轉
- 來源：VP-9299 辯論挖出。原 ticket 建議「else 分支套 options?.x ?? default 或刪掉 options 參數」。
- **關鍵事實（改變修法方向）**：Azure Event Hubs Kafka 的 session.timeout.ms 允許範圍
  **6000–300000ms**（azure-event-hubs-for-kafka CONFIGURATION.md）。caller 要的 950000 若真的
  傳下去，broker 直接拒 JoinGroup（INVALID_SESSION_TIMEOUT）→「尊重 options」的天真修法會把
  三個 consumer 在 prod 弄到起不來。
- kafkajs 2.2.3 實測（node_modules 讀碼）：client 端不 clamp sessionTimeout（broker 拒絕）；
  唯一 client 驗證是 heartbeatInterval >= sessionTimeout 會 throw；rebalanceTimeout 確實對應
  protocol 的 rebalance_timeout_ms（= Java max.poll.interval.ms 槽位）；**kafkajs 沒有背景
  heartbeat**——只在訊息之間送，controller 裡 `heartbeat` 參數被 destructure 但全檔 0 個呼叫點
  → 單一慢訊息不受任何 timeout 調整保護。
- Prod 永遠走 else 分支（ConfigMap envm=prod）→ 45000 是「今天實際在 prod 運作」的值；
  950000 從未在 Azure 路徑生效過，沒有任何 prod 證據支持需要它。
- 三個傳 950000 的 caller：consume_result_ready(:908)、consume_skin_care(:5020)、
  consume_skin_care_report_result(:5837)。其餘 8 個 controller caller + pns.service.ts:10934
  不傳 options。

## Approaches Considered

### [2026-08-27] 反方（Explore subagent）判定 REVISE，修法轉向
- 我的原案（clamp 到 300000 + rebalanceTimeout=max(...)）被否決，三個理由：
  (1) 算術踩界：clamp 後 session=300000、rebalance=max(120000,300000)=300000，Event Hub 要求
  max.poll.interval **嚴格大於** session → 唯一會觸發 clamp 的情境剛好落在違規邊界上；
  (2) 升 session 45s→300s = 犧牲活性偵測：pod OOM/rolling deploy 時 partition 最多懸置 5 分鐘
  ×3 replicas，用保證的可用性退化去換一個假想的收益；
  (3) 就算升了也治不了本——kafkajs 無背景 heartbeat，慢訊息的真兇是 getRequest 無 axios
  timeout（VP-17753 的修法才是根治）。
- **採納方案**：刪掉三個 caller 的 `{ sessionTimeout: 950000 }` 參數 + 刪掉 createConsumer 的
  `options` 參數（else 與 stprod 分支都改為明寫現行 default）。Prod 行為零變化；staging
  （stprod 分支）那三個 consumer 950s→95s（僅 staging，且 17753 的 timeout 修掉了長訊息根因）。
  這正是原 ticket 給的第二選項：divergence 是刻意的，就讓 caller 停止相信 options 有效。
- 測試 seam：抽 `resolveConsumerConfig(envm, ...)` 純函式可行，但刪參數方案下更簡單——
  行為不變 + type check 保證無 caller 再傳 options；mock kafka client 斷言 config 是套套邏輯，不做。
