### Ground truth found in code (2026-08-31)
- The date already exists and is live: `isAccessionClaimable` returns `consultDate` (`accession-claim.service.ts:249-274`, `accession-claim.model.ts:44`), shipped under VP-17868, merged to `main` 2026-08-24T18:38Z (#583) and `stage_test` 21:40Z (#584). transv2 is push-to-deploy → in prod. Local files verified identical to `origin/main` (`git diff HEAD origin/main -- src/calendar/models/accession-claim/` → empty).
- Disclosure is **gated**: `viewerIsTiedToClaim` (service.ts:276-296) discloses the date only when the caller is `claimed_by`, the holding event's creator, or a participant. Rationale (VP-17868): `isClaimable` accepts any accession id and never checks clinic ownership, so an ungated date turns the query into a probe for other practices' bookings.
- The FE gets claim status **on row click, not from search**: `SearchOrders.vue handleClickOrder` fires `checkIsAccessionClaimable(accessionId)` (GraphQL, transv2) in a `Promise.all` alongside two `/trans/*` REST calls. The search itself is `loginServiceCloud.post('/trans/findPatient')`.
- `/trans/findPatient` lives in **LIS-transformer (v1)** — `src/trans/trans-patient-search.controller.ts` / `getPatient.service.ts` — a different service from transv2, with no access to `calendar_prod` claim data.
- `getClaimedAccessionIds` (resolver.ts:31-41) already exists as a bulk query, but returns **all** claimed ids for practice 150105 (3,514 rows as of VP-17868's readback) with no dates, and has **zero consumers** (grepped va-portal + vibrant-wellness-portal). Unsuitable: full-list disclosure to any clinic user, and no date.

## Approaches Considered
- **A (recommended): new batched GraphQL query in transv2.** e.g. `accessionClaimStatuses(accession_ids: [String!]!): [AccessionClaimStatus!]!` → `{accession_id, claimable, currentEventId, consultDate}`. One `findMany` with `accession_id in`, same clinic-user guard, same `viewerIsTiedToClaim` gate per row, input capped (~20, matching `searchResultLimit`) so it cannot be used to enumerate. No schema change, no migration. FE calls it once per rendered list (search results *and* the recent-orders list) → row labels + banner date from one round trip.
- **B: nothing on BE.** The banner date already works via `isAccessionClaimable`. Cheapest, but does not deliver VP-18051's row-level label, which needs status before the click.
- **C: put the data in `/trans/findPatient` (literal reading of the AC).** Rejected: cross-service coupling (v1 → calendar_prod), and that endpoint also serves the patient page, so the blast radius is far wider than the modal.

## Decisions Made
- **Leo chose Approach A (2026-08-31)**: batched GraphQL query in transv2. No Jira comment for now — draft it after the work is done.
- Batch cap set to 20 (`MAX_CLAIM_STATUS_BATCH`), matching the modal's `searchResultLimit`. It is a probing limit, not a performance one: the query takes arbitrary accession ids and never checks clinic ownership, so an uncapped batch would sweep for other practices' bookings in one call.
- Extracted `CLAIM_DISCLOSURE_SELECT` + `toClaimResult()` so `isClaimable` and `claimStatuses` share one mapping. Two independent copies of the disclosure gate is exactly the drift the "sync sibling encodings" lesson warns about — the gate is a privacy control, and a batch path that quietly disagreed with the single path would be invisible.
- Result carries `accession_id` per row and preserves request order, so the FE can zip it against its rendered list without a second lookup.

## Retrospective
- **Assumption vs outcome.** The opening read was "this is probably already done" — VP-17868 shipped the date a week ago. That was right about VP-18050's own acceptance criteria and wrong about the deliverable. The work only became visible after reading the *sibling* ticket: VP-18051 wants a row-level label, which needs the status for the whole list before any click. A ticket split across BE/FE can hide its own requirement in the other half.
- **The AC named the wrong endpoint.** "Search-result response" reads as `/trans/findPatient`, which is in a different service (LIS-transformer v1) with no access to the claim data. Taking it literally would have meant wiring v1 into `calendar_prod` for a modal. Checking which repo actually serves the call the FE makes cost one grep and changed the design.
- **Batching a gated field is a privacy change, not a performance one.** The disclosure gate exists because the query never checks clinic ownership. A batch endpoint over the same data multiplies exactly that exposure, which is why the cap is in the code with its reason written next to it rather than left as a tuning knob.
- **Down-push check (ENFORCEMENT-LADDER).** The one candidate for a deterministic mechanism is "a batch path and its single-id path must not disagree" — currently held by a shared `toClaimResult()` plus a cross-check test. That is structure, not prose, so it is already one rung above a lesson. No new hook or CI gate proposed.
- **Confidence: 4/5.** Independent through analysis, design, implementation and live verification; Leo's input was needed only for the approach choice and the FE scope call.

## Lessons Learned
- When a ticket is one half of a BE/FE split, read the other half before deciding the work is already done. The acceptance criteria of one half routinely omit the requirement that makes the other half possible.
- A PM's acceptance criterion that names *where* data should appear ("in the search response") is a statement about the user-visible surface, not about the service that serves it. Verify which service actually backs that call before designing to the sentence.
- A test that asserts "request is rejected" must confirm it was rejected by the layer under test. Auth stacks reject early and for other reasons, and the assertion looks the same either way.
- Adding a batched form of an endpoint whose response is access-gated is a security review, not a convenience refactor: the gate has to be re-applied per row, and the batch size becomes an exposure limit.
