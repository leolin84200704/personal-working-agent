## Findings — inbound order mechanics (Explore agent, origin/main ebb104f)

### [2026-08-19] Requirement-by-requirement ground truth (inbound side)
- **#1 Billing**: charge method decided by **IN1-2.1** — exactly `'C'` (uppercase) =>
  `customerPay` (charge card on file via charging allSharedPaymentMethods + transactionPay
  walk, VP-17538); anything else incl. missing IN1 => `patientPayLater` (patient gets pay
  link email — the opposite of what Prospera wants #4 to prevent!). parser.service.ts:588-592,
  order-finalizer.service.ts:44-206. HL7 path does NOT block order on charge failure
  (no failOnCustomerPayFailure), just records emr_payment_fail_reason.
- **#4 Practice contact**: patient email is read from **PID-20.1** (nonstandard — NOT
  PID-13.4), phone from PID-13.1 (digits-only normalize). NO practice-contact-override
  mechanism exists; vendor would simply put practice email/phone in those fields. No
  validation would reject it. WARNING: values overwrite stored patient contact record via
  updateContactIfChanged (gRPC UpdatePatientInfo) on EVERY order — all patients at the
  practice converge to practice contact. patient-detail-parser.service.ts:100-174.
- **#5 Kit/collection**: per-integration ONLY (`ehr_integrations.kits_options` 0/1/2;
  0=non-blood ship to patient + blood supplied by clinic, 1=everything ships to patient,
  2=clinic stocks everything). NO per-order HL7 field/override exists — if Prospera needs
  per-order choice, that is NEW DEVELOPMENT. kit_delivery_option column is onboarding
  metadata, unused by pipeline. parser.service.ts:784-798.
- **#3 Test codes**: OBR-4.1, whitespace stripped. Formats: discountpanel{id},
  ??REQU (VAREQUISTION*, chars3-6 case-insens), ??TEST (VATEST*), VACP{id} (case-SENSITIVE),
  bare numeric (custom bundle), VASC{id} shortcuts. isOrderable==='true' required for
  REQU/TEST branches only. Unknown/not-orderable code => whole order fails (no partial),
  retryable x5. Catalog from pricing getLegacyPackagePriceMapping / getPackage2TestMapping /
  getLegacyBundleMapping, 30-min cache.
- **Envelope**: ORM^O01 (OML^O21 auto-rewritten); MSH-9 not actually validated; needs MSH +
  >=1 ORC. ORC-12.1 = ordering provider (<=7 chars => customer_id, else NPI); last ORC wins;
  OBRs are message-global (multi-ORC duplicates tests). MSH-10 = dedup control_id (same id
  short-circuits to prior sample). File pickup: sftp_folder_mapping (use_v2_pipeline=1,
  pipeline_location) + creds from ehr_vendors by emrName; only *.hl7/*.HL7; same
  path+filename never re-ingested (resends need new filename); remote file moved to
  archive/ after fetch; 15-min cron. hl7-order-fetch.service.ts.
- **Vendor-spec gotchas list** (8 items) captured in agent report — key ones: PID-20 email,
  IN1-2.1 'C' only, one bad OBR fails whole message, filename uniqueness, MSH-10 freshness,
  kit per-integration, charge-fail doesn't block HL7 order, PID contact overwrite.

## Findings — requisition / test menu / result delivery / onboarding (Explore agent 2)

### [2026-08-19]
- **#2 Requisition form: DOES NOT EXIST for EMR vendors** — ticket's "supported" claim is
  wrong. emr-v2 has zero requisition-document mechanism (all "requisition" hits are the
  VAREQUISTION test-code prefix). Nearest artifacts: LIS-transformer JWT-gated
  GET /trans/getRequisitionForm?sample_id= (proxies legacy private-IP
  192.168.60.77:8081 FetchScannedRequisition — SCANNED req, not blank form);
  order-management pdf_gen_service.go has NO REQUISITION_PDF type (has ORDER_SUMMARY,
  BLOOD_DRAW, NY_FORM, COLLECTION_INSTRUCTION...). Options: new emr-v2 SFTP push /
  order-management PDF type / token-gated wrapper.
- **#3 Test menu: no vendor-facing API.** Internal pricing endpoints all JWT-gated
  (shared-secret HS256; no partner auth model): getLegacyPackagePriceMapping gives
  id/orderTypeId/name/displayName/priceVa/priceVw/isOrderable/uniqueemrcode/taxCode —
  no images, no specimen info, no TAT. productMap (VP-17475) is resolve-only, internal.
  /quote not found anywhere. **Test images: confirmed absent** (only kit/tube images in
  LIS-Sample lis_inventory_master.kit_assets). 2026-06-17 huddle conclusion stands:
  emr-v2 should NOT become catalog publisher; per-customer orderable catalog belongs
  upstream. Practical: static/periodic code list to Prospera (VP-16987 scheduled-reports
  SFTP CSV is a delivery precedent).
- **Outbound results**: ORU^R01, v2.3 default; MSH-5 = ehr_vendors.code, MSH-6 =
  msh06_receiving_facility; PDF embedded base64 in OBX|1|ED|PDF^PDF||^AP^^Base64^...
  (add_report 0/1/2 from report_option CLASSIC/PERSONALIZED); file named
  {emr_order_id|sample_id}.hl7, put to sftp_result_path; no ACK/MSA anywhere; fan-out
  deduped on (legacy_emr_service, sftp_result_path); result_push_level enum for partials.
- **Onboarding surface**: Prospera must supply vendor code (→MSH-5), HL7 versions, SFTP
  host/port/user + password or PEM private key (key preferred; BIOINSIGHTS precedent),
  order/result paths; per-practice: msh06, NPIs, report_option, kits_options,
  result_push_level. Inbound polled 15-min from sftp_folder_mapping.server_folder,
  post-fetch move to {server_folder}/archive (hardcoded subdir; sftp_archive_path NOT
  read by fetch). BUG found: both SFTP connection-test endpoints
