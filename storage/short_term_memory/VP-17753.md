- 失效鏈（main@b3aa013，行號現值）：`getRequest`（:15904-15929，catch 無 return、axios 無 timeout）
  → 兩次呼叫皆敗時 `report_list` undefined（:1448-1461）→ `report_list['finished_reports']`
  （:1483/:1514）throw → eachMessage 外層 catch 吞（:1611）→ autoCommit 已 commit +
  acquireEventLock 已寫永久 trigger_history row（:236-253）→ 同 event replay 永遠被擋。

## Approaches Considered

### [2026-08-27] 方案與辯論（反方 = Explore subagent，全文結論收錄）
- **Option A（fail-open，推薦）**：view_report_link 才是 payload，product list 是裝飾。
  (a) getRequest 加 axios timeout + catch 明確 `return null`；(b) :1483/:1514 改
  `buildProductList(report_list?.['finished_reports'])`（buildProductList 對非 array 已回 ''）；
  (c) 降級送出時寫 `failed_notification`（reason 標明 email 已送出、缺 product list）。
- Option B（fail-closed + failed_notification skip send）：否決——為裝飾性欄位擋掉核心通知。
- 反方 CONFIRM + 兩個補強：(1) token 先於 getRequest 建立（:1354），今日 throw 會留下孤兒
  report_email_tokens row（45 天效期、從未寄出）——fix 順帶止血，prod 既有孤兒 rows 待盤點；
  (2) `failed_notification` 全 repo 只有 writer 沒有自動 retry reader（operator 手動恢復）→
  寫降級紀錄不會觸發自動重寄。
- 反方風險提醒：兩次 getRequest 無 backoff，timeout 10s ⇒ 最壞 +20s/message，回踩 VP-17754 的
  session timeout 問題 → timeout 取 5s。Postmark template 35058386/38859237 對 product_list=''
  的渲染未驗證（repo 外的驗收項）。
- getRequest 共用面：live call sites 僅 :1448/:1455 + pns.service.ts:13048（後者回傳值從未被讀，
  死 fetch）→ 加 timeout blast radius ≈ 0。null vs undefined：isEmpty 兩者皆 true，行為不變。

## Decisions Made

### [2026-08-27] Leo 核可 fail-open 方案
- timeout 定 5s（兩連打無 backoff，最壞 +10s，不回踩 session timeout）。
- 降級送信寫 failed_notification（僅 writer、無自動 retry reader，已驗證不會重寄），
  reason=product_list_fetch_failed_email_sent_degraded；記錄動作整段 try/catch——
  記錄失敗不得再把信弄丟（那正是本票要修的 bug）。
