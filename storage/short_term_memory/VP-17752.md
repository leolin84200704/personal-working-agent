# VP-17752 — isOrderable=false rejects the whole EMR order

## How it presented
Found by a manual 24h health sweep on 2026-08-18, not by any watch. `hl7_file_input` 6848,
`/parsley-la/orders/`, MDHQ, received 2026-08-12 21:00Z, retries spent by 21:46Z, then six
days untouched: `parse_finished=0`, `sample_id=NULL`, `retry_num=0`, `error_detail=NULL`.

## Root cause (evidence, not inference)
The HL7 file (read from the on-prem pod's retained copy) carries 9 OBR codes. Live
`getLegacyPackagePriceMapping` gives a perfect split:

| code | test | isOrderable | outcome |
|---|---|---|---|
| VATEST2287 / 2280 / 2259 / 2276 / 2277 / 2279 | Vit D, B12, Selenium, B1, B2, B6 (serum) | false | rejected |
| VATEST56 / VATEST38 / VAREQUISTION74 | Iron, Ferritin, Omega-3&6 | true | accepted |

`obr-parser.service.ts` resolves the code, then gates on `pkg.isOrderable === 'true'`
(line 246 VATEST, line 225 VAREQU). A non-orderable item becomes an OBR error, and **one OBR
error rejects the entire order** — the three orderable tests died with the six.

85 of the 300 entries in the mapping carry `isOrderable=false`, so the exposure is wide.

## What was NOT the cause (each refuted by evidence, in the order I tried them)
1. *Mapping data missing* — all nine codes present in the live API.
2. *Codes added after 08-12* — `package_price_mapping` rows created 2021, last touched
   2025-03-20.
3. *Customer-resolution mismatch* (the skill's headline gotcha) — irrelevant here:
   `emrCodeToPackagePriceMap` / `testOrderTypeIdToPackagePriceMap` are not customer-scoped.

## Recurrence
`hl7_file_input` 6556, 2026-07-08, same folder, byte-identical six codes, also still stuck.
Two orders, one month apart, both invisible.

## Fixes
- **PR #375 (draft → staging)**: `ObrErrorReason = 'unknown_code' | 'not_orderable'` on the
  classifier; `last_error` names the not-orderable subset + an ERROR log stating retrying
  cannot place the order. `emr_code_not_found` keeps the bare code list (daily triage reads
  that column; ~4,700 historical rows share the shape). Retry semantics unchanged. API path's
  `unrecognized_test_codes` deliberately left alone — VP-17691 contract.
- **DECIDED (Leo 2026-08-18): the catalog is right.** "照之前規則不該就是不該" — the flag is the
  rule, not a gap to fill. Consequences: the six tests stay non-orderable; MDHQ/Parsley LA's
  menu is stale and must stop offering them; **6848 and 6556 can never be recovered, only
  replaced** (the providers have to re-order, and nobody has told them yet).
- Behaviour changed to match the ruling: the not-orderable class is now **terminal** —
  `parse_finished=true`, `retry_num` untouched, Sentry alert on the **first** attempt instead
  of after five futile refusals over ~46 min. An unrecognised code stays retryable and alerts
  at exhaustion, because that one really can be fixed by provisioning. Side effect to
  remember: terminal rows leave the `parse_finished=0` "still stuck" view, so Sentry is the
  only surfacing path for this class now.

## Wider findings recorded on the ticket
- **55 orders never recovered** from `emr_code_not_found` (4,733 tagged since 2024-12-03),
  spanning 2025-04 → 2026-08: 17 VACP bundle, 12 other VATEST, 9 raw exceptions stored in
  that column, 6 VAREQU, 5 discount panel, 4 other, 2 this class.
  `/parsley-la/orders/` alone is 15 of the 55. **Nothing surfaces retry exhaustion** — worth
  its own ticket (suggested, not created).
- **`lis_emr.package_price_mapping` contradicts the live API**: all six read
  `isOrderable='TRUE'` in the table, `false` from the API. Triage from the table points away
  from the answer. Decide whether that table is authoritative for anything.

## The real gap: alerting was dead in prod (found 2026-08-18 after Leo's push-back)

Leo's framing: blocking the order is correct, the bug is that nobody was told, because
PM/marketing have to do the follow-up. Two halves:

1. **`SENTRY_DSN` was never set in production.** VP-17544's Sentry path (→ `#emr-orders-bot`)
   had the DSN only in the STAGING ConfigMap (`emr-v2/lis-emr-v2-config`, 71 chars,
   `sentry1.vibrant-america.com` project 49, `SENTRY_ENVIRONMENT=staging`). Both prod pods —
   AKS *and* on-prem — logged `SENTRY_DSN not configured — error reporting is disabled` at
   every boot. **No order-abandonment alert has ever fired in production.** That is the
   whole reason 6848 and 6556 were invisible.
   Fixed: DSN + `SENTRY_ENVIRONMENT=production` written to `lis-emr-v2-config-prod` in AKS
   `default` (the copy Jenkins syncs on-prem), AKS `emr-v2`, and the on-prem ConfigMap;
   backups in scratchpad `cm-backup/`; both prod pods restarted and now log
   `Sentry initialised (environment=production)`.
   **Channel proven live, not merely initialised**: a test event from inside each prod pod
   returned `HTTP 200` + event id from project 49 (two events tagged
   `failure_class=channel_test`).
2. **One class for every cause.** Everything abandoned reported as `retry_exhausted`, so no
   alert rule could target a specific cause. Now `test_code_not_orderable` /
   `test_code_not_found` / `customer_not_found` / `retry_exhausted` (default).
   Abandonment stays the trigger (Leo 2026-08-03) → one stuck order, one message, ~46 min
   after arrival.

Still open: a Sentry alert rule on `failure_class` for the classes PM should act on (events
now arrive; routing is a Sentry-side setting, untouched — Leo acked 2026-08-18). Moving
`SENTRY_DSN` and the Kafka SAS out of the ConfigMaps into Key Vault is now tracked as
**VP-17756** (Leo: "未來會做").

## Reusable
- `emr_code_not_found` is a dumping ground: unknown codes, not-orderable codes, unprovisioned
  bundles, and raw stack traces all land in it. Never read it as "code missing".
- To test a code's orderability, call the live pricing API — **not** the mirror table.
- Splitting the failing vs succeeding codes within one order was what located the cause; the
  boundary (6 fail / 3 pass) was the whole diagnosis.
- **"The alerting exists" is not "the alerting fires."** VP-17544 shipped working code into an
  environment with no DSN, and the boot log said so at every start for weeks. Before trusting
  any alert path, read the pod's own startup line and then send one real event through it —
  `Sentry initialised` still only means a DSN parsed.
- The DSN was present in staging and absent in prod, which is the same shape as the VP-17559
  Key Vault break: config verified in the easy environment and assumed in the other.
