(Dev In Progress). This story = the EMR/HL7 leg. Status Dev To Do, assignee Leo, P2.
Sibling stories: VP-17540/41/42 (FE, Zhiheng), VP-17543 (BE patient-creation + owns the

Relevant PRD numbers: 1.08% of 2026 YTD orders missing DOB and/or Sex (1,340/123,632);

### Ground-truth findings (emr-v2 @ origin/main, read-only exploration)

1. **Sex is structurally undetectable today — silent data fabrication.**
   `src/modules/hl7-order-processing/services/patient-detail-parser.service.ts:127-128`:
   raw PID-8 is lowercased, then `=== 'f' || === 'female'` → `'Female'`, **everything else
   → `'Male'`**, including empty / missing. Verbatim Java-parity branch (the file's own
   docstring line 29-31 calls it "questionable"). Consequence: the downstream blank check
   at line 206 (`isBlank(p.patient_gender)`) is **dead code on the HL7 path** — a missing
   PID-8 produces an order with a fabricated **Male** patient. Interception therefore has
   to read the RAW PID-8 value *before* normalization; it cannot hang off the existing
   required-field check.
   (Related history: VP-17471 fixed case-sensitivity so 'F'/'FEMALE' stopped becoming Male.)

2. **Missing DOB does fail, but is mislabeled and then dies silently.**
   blank PID-7 → `findOrCreatePatient` logs + returns null (lines 205, 211, 213)
   → `parser.service.ts:300-303` returns `{ error_codes: 'parse aborted' }`
   → `processors/hl7-order.processor.ts:159-171` writes that string into
   **`hl7_file_input.emr_code_not_found`** and decrements `retry_num` (VP-17120 made this
   class retryable, `parse_finished` stays false).
   Two defects fall out: (a) error class **collides with test-code mapping failures** — per
   LTM emr-integration.md's triage table `emr_code_not_found` routes to the Order team for
   bundle creation, i.e. wrong owner, wrong playbook; (b) retrying the same file with the
   same blank field can never succeed, so once `retry_num` hits 0 the row sits
   `parse_finished=false, retry_num=0` forever with **no alert** — exactly the silent
   failure the PRD forbids.

3. **There is no ACK channel on the SFTP HL7 path.** Inbound orders are files pulled off
   SFTP (`services/hl7-order-fetch.service.ts`), not MLLP.
   `modules/hl7/services/hl7.service.ts:73-80` `generateAcknowledgment` is an unwired stub
   (TODO comment, zero callers, no transport). → **PRD Open Q2's "reject with error in ACK"
   is not implementable for SFTP vendors in this release.** PRD §7 itself parks
   provider-facing feedback in Phase 2 ("EMR order-level error feedback to providers
   … folds into the EMR delivery acknowledgment roadmap"), which corroborates this.
   Real options: reject-and-record (+ internal alert) or accept-and-hold.
   The synchronous JSON/API intake path (`order-intake/`) *can* answer inline and already
   does for eligibility failures (`kind:'ineligible'` + `failures[]`,
   `order-intake-enrichment.service.ts:204-215`).

4. **The practice-level flag already has a mechanism — no new infra needed.**
   Ticket's "Beta list name: mandatory_dob_sex" maps to the org's `betaProgram` /
   `beta_program_participations` tables (clinic_id + customer_id + isActive), seen in
   `LIS-backend-coreSamples/src/customer/customer.service.ts:9421-9467`. emr-v2 already
   consumes them: `modules/grpc/services/grpc-client.service.ts:536-597`
   `fetchCustomerBetaPrograms` / `FetchCustomerBetaProgramsForClinic` (**v1 only — v2
   beta_programs data is incomplete per Leo, line 543**), the same gate VP-17117 uses for
   `gz_ny`. Caveat: the gz_ny gate deliberately **fails OPEN** (NY compliance first,
   `grpc-client.gz-ny-gate.spec.ts:24`). This one must **fail CLOSED** — an RPC blip must
   fall back to legacy behavior, never block every EMR order.
   Note the gate is per (customer, clinic), so it can only be evaluated *after* customer
   resolution — the check has to sit after `customerFetcher.fetchByNpi`, not at PID parse.

5. **No alerting infrastructure exists in emr-v2.** No Slack / webhook / pager anywhere in
   the service. Per VP-17412 (Leo's decision) HL7-failure diagnostics live in the **agent
   layer**: the daily `DailyJob/hl7_fail` triage job writes `hl7_file_input.error_detail`,
   while `last_error` (VP-17533) holds app-written bare facts. So AC3's "dedicated alert
   channel … same business day" is a product/ops decision, not only code.
   Risk to name out loud: dream 2026-08-01 flagged 3 automation jobs failing silently, so
   leaning on the agent job as Support's SLA channel is fragile.

6. **Real-world EMR volume is ~0.** VP-17286 full audit (2026-07-15, recorded in LTM
   emr-integration.md:711): 1,884 of 2026's raw HL7 order files across every vendor →
   **0 missing PID-7/PID-8**, cross-checked against 1,527 patient records → also 0.
   Consistent with the PRD's own numbers (DOB ~0%; the gap is a portal Sex problem).
   This already discharges PRD §5.1 "Identify EMR practices currently sending empty
   fields": there are none in 2026, so "near-zero EMR interception at launch" holds before
   we write a line of code. Address completeness was not audited.

## Approaches Considered

Debate step done inline (session constraint: no subagents). Risk class = code change on the
prod order-ingestion path → not Routine.

**A. Reject-and-record, terminal, distinct error class, beta-gated (recommended).**
Check raw PID-7/PID-8 after customer resolution, before patient resolution, only when the
resolved (customer, clinic) is in `mandatory_dob_sex`. New parse-result field
(`patient_info_incomplete: 'dob' | 'sex' | 'dob,sex'`); processor writes a stable
machine-readable tag to `last_error` (e.g. `missing_patient_demographics=dob,sex`), leaves
`emr_code_not_found` NULL, sets `parse_finished=true` (terminal — a re-parse of the same
file can never succeed), leaves `retry_num` untouched. Normalization at line 128 is left
alone, so flag OFF = byte-for-byte legacy behavior (rollback requirement, PRD 4.2-10).
- For: no schema change; no new infra; correct owner routing; honest terminal state instead
  of a row that quietly runs out of retries; small blast radius; near-zero live volume.
- Against: order is dropped with no provider-facing feedback until the Phase-2 ack
  roadmap — Support has to phone the practice. Terminal also means the retry-rescan can't
  rescue it if Support fixes something upstream (but nothing upstream *can* fix it: the
  patient does not exist yet, the defect is in the vendor's file).

**B. Accept-and-hold.** Keep the row retryable with a large `retry_num` so it self-heals
if the data appears.
- Against: nothing can make the data appear — the check reads the inbound file, not a DB
  patient, and the vendor's resend arrives as a *new* file with a new MSH-10 anyway. Hold
  therefore degenerates into A with a slower, noisier failure. Rejected unless EMR Eng
  wants hold semantics for a reason I can't see.

**C. Reject in ACK (PRD's other Open-Q2 branch).** Not implementable this release —
finding 3. Would need an MLLP/ack transport that does not exist.

**D. Push the check upstream into the eligibility API's IncompletePatientInfo rule.**
The HL7 path does not call eligibility check at all (only `order-intake-enrichment` does),
so this would mean wiring eligibility into the HL7 path — far larger change than the story,
and it would alter placement behavior for every HL7 order. Rejected for this release.

### [2026-08-03] 測試抓到我 code 的真實缺陷：bare `void` 造成 unhandled rejection
`void this.slackNotifier.notifyEmrOrderFailure(...)` 沒有 attach catch handler。
notifier 自己保證不 reject，所以實務上安全 —— 但只要它被改壞或換實作，rejection
就會變成 unhandled rejection，**Node 會直接結束 process**，等於「告警失敗導致 pod 掛掉」。
測試（mockRejectedValue）直接讓 jest worker crash 才暴露出來。修法：try/catch 包同步
throw + 顯式 `.catch()` 接 async rejection，兩個方向都關掉。
**教訓：fire-and-forget 的 `void` 不是「安全地忽略」— 它只忽略回傳值，不忽略 rejection。
凡是不 await 的 promise 都必須有 .catch。**

### [2026-08-03] 誤用 `rg -r` 汙染了好幾輪探索結論
`rg -rn 'pattern' path` 中 **`-r` 是 `--replace`**，`-rn` 被解析成 `-r n` → 把每個匹配
內容替換成字面 `n` 再輸出。所以我看到 "eligibility" 變成 "lnility"/"liy"/"n"，
**我還誤判成終端顯示層在吃字元**（甚至聯想到 memory 裡的 WezTerm hyperlink_rule 事件）。
同一輪還用了 `--include='*.go'`（那是 grep 的語法，rg 要 `-g`）配上 `2>/dev/null`，
把 rg 的 unknown-flag 錯誤吞掉 → **假的「0 hits」**，讓我一度以為 order-management
沒有任何 DOB/Gender 處理。
**教訓 (a)**：短選項簇不要跟需要參數的 flag 混寫（`-rn` ≠ `-n -r`）。
**教訓 (b)**：`2>/dev/null` 會把「工具用錯」偽裝成「查無資料」。搜尋若回 0 命中，
先確認命令本身有沒有報錯，再下結論。
**教訓 (c)**：輸出看起來被亂改時，先懷疑自己的命令，再懷疑環境。我上次（Jira link 事件）
的正確答案是「顯示層」，這次同樣的直覺是錯的 —— 前一次的結論不是這一次的先驗。

### 2. 失敗分析

| 失敗 | 根本原因 | 可預防？ | 代價 |

| 誤用 `rg -r`（3 次） | `-r` 是 `--replace`，`-rn`/`-ril` 把後續字母吃成 replacement 值並停用 `-i`/`-l`/`-n`。錯誤不報錯，只是降級成另一個搜尋 | 可 —— flag 分開寫 | **最貴**：兩次把錯結論回報給 Leo，一次誤判成終端顯示層問題 |
